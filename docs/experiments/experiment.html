4.7.3 Verification Recovery

Verifier 不能完全消除大分组造成的信息遗漏。LoCoMo 从 W4 到 S8 时 final source coverage 由 84.3% 降至 65.7%；LongMemEval-S 到 S8 仍有 90.4%；BEAM 到 S1 仍有 97.6%。LoCoMo S16 的 verifier gain 进一步降至 2.0 个百分点，说明该设置已经超出稳定工作区间。

4.8 Evidence Preservation

NativeMem 始终完整保留 Source Memory；本节评估 Temporal 和 Topical Abstract Memory 在统一实际长度曲线上显式引用了多少原始历史，以及是否保留 LoCoMo 标注的回答证据。LongMemEval-S 只有 session-level evidence，BEAM 没有 gold evidence IDs，因此 gold-evidence 分析只使用 LoCoMo。

结果。 W4–S8 范围内，gold-all coverage 的下降明显小于全历史 source coverage 的下降，说明 Abstract Memory 优先保留了与问题证据重合的 source turns。S16 同时出现 source coverage、gold coverage 和 Luna QA 的明显下降，因此不作为默认设置。所有配置的 reference precision 均为 100%，变化来自 source omission，而不是无效引用。未被 Abstract Memory 引用的内容仍保存在 Source Memory 中。

解释边界。 Gold coverage 只检查 gold source IDs 是否出现在 Abstract Memory 的有效引用集合中。它不验证摘要文本是否准确表达 source turn，也不证明检索阶段会访问该 entry 或最终答案一定正确。因此，本节支持的是 evidence traceability under compression，而不是完整的 semantic construction quality。

Agent-Controlled Hybrid Retrieval（2026-07-31）

方法定位：文本文件是权威记忆状态；grep、BM25 和 Embedding 是三个并列的检索工具，目录、timeline、links 和 read_original 提供结构化访问。LLM 自主决定调用哪个工具、使用什么 query、是否继续检索。BM25 与 Embedding 索引都可以从文本文件重建，不保存唯一事实。

条件变化目的
File-onlyAgent 使用目录、文件和 grep冻结文件导航基线
BM25-only每个 query 固定执行 BM25，再由统一 LLM 回答词法检索基线
Embedding-only每个 query 固定执行 Embedding search，再由统一 LLM 回答语义检索基线
NativeMem RetrievalAgent 自主选择 grep、BM25、Embedding 和结构化访问工具验证 Agent-controlled retrieval
ByteRover-styleexact/fuzzy cache → BM25 → single LLM → full agentic search主要策略对标：固定五级路由
Semble-styleBM25 + Embedding + RRF + 记忆结构重排后续混合检索增强

所有条件复用同一批已构建 memory、同一题集、answerer、judge 和工具预算。报告任务成功率或最终准确率、工具调用数、可见 token、延迟、直接成本和索引大小。主要比较 NativeMem Retrieval 与 ByteRover-style。

4.4 Scaling with Model Capability

我们的方法和 embedding-based 方法（Mem0/A-Mem 等）有一个本质区别：我们的全流程（存储、组织、检索、回答）都由 LLM 完成，而它们的检索环节不依赖 LLM（靠 embedding + BM25）。

这意味着随着 LLM 能力提升：

  • Ours：存储更全、组织更好、检索更准、回答更好——全链路受益
  • Embedding-based：存储和回答受益，但检索质量受限于 embedding 模型——部分受益

实验设计：在同一个 benchmark（LoCoMo）上，用不同能力等级的模型跑所有方法，画 scaling 曲线。
