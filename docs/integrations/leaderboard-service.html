Competition Branch · Add / Search Service

在 gpt-4o-mini 上让记忆真正写得进、查得快

学术赛道规定 Add 与 Search 使用 gpt-4o-mini。这条路径原本每次 Add 都返回 200，实际写进记忆的 topic 文件只有 1 字节。本文记录故障链、修法，以及修完之后仍然敞着的问题。

competition 分支 · Add / Search 服务 · gpt-4o-mini

§1 服务契约

平台自己负责 Answer 与 Eval，这个服务只有两个同步接口。

接口职责约束
POST /add同步写入一个用户的一批消息返回 200 即表示已提交且可检索
POST /search返回该用户记忆中的证据只返回证据，不合成答案
GET /health存活探测无鉴权

user_id 是唯一的检索隔离键，一个 user_id 一个工作区。一次 Add 最多 20 条消息，平台会并发 64 个 Add、256 个 Search，单请求超时 1200 秒。

§2 gpt-4o-mini 上原本不工作

这不是"效果差"，是完全没有写入。Add 每次返回成功，topics/ 下的文件却只有 1 字节；检索之所以还能返回东西，全靠 sources/ 里逐字归档的原始消息在撑。真正的语义记忆一条都没有建立起来。

2.1 故障链

  1. 提示描述的工具不存在

    management_tools() 只返回一个 shell。Claude Code 自带 Read / Write / Edit / Grep / Glob，所以论文那条路径没问题；OpenAI 兼容路径没有任何内置工具，模型手里只有 shell，而写入提示通篇要求它"用 Write 和 Edit 工具"。

  2. 模型退回 echo > 文件，撞上格式契约

    Topic 契约要求每个新段落带块 ID、每条引用有脚注定义、每个脚注指向已归档的来源。手写这套标记，弱模型过不了。

  3. 拒绝信息不说缺什么

    修复指引其实早就写好了，但只在整轮 agent 跑完、事务提交被拒之后才发出。而模型是在运行途中反复撞同一个错，20 轮全部耗尽，根本走不到那一步。

  4. 同一条失败命令重复 36 次

    stop=max_turns，输入 token 烧到 18 万，工作区回滚，什么都没落地。Add 依然返回 200。

2.2 现场记录

给 OpenAI agent 补上轨迹记录之后，第一次看清它在做什么：

19 shell echo "# Caroline\n\n## Support Group… → TopicFormatError: undefined footnote: e1 20 shell echo "# Melanie\n\n## Painting… → TopicFormatError: undefined footnote: e1 21 shell echo "# Caroline and Melanie… → TopicFormatError: undefined footnote: e1 …同样三条命令原样重复 12 轮，直到轮次耗尽… 54 shell echo "# Caroline and Melanie… → TopicFormatError: undefined footnote: e1

在补上轨迹记录之前，日志里只有 rounds: 20, stop_reason: max_turns，看不出它是做完了工作还是在原地打转。前两轮优化我就是靠猜做的，两轮都做错了方向。

§3 写入：把判断留给模型，其余写死

结论是不该让弱模型手写契约标记。项目本身的原则就是"标识符由 Runtime 分配"——那就贯彻到底：模型只交内容，标记由运行时生成，契约无从违反。

3.1 remember 工具

模型给出主体、主体类别、事实原文和来源 [ref]；文件路径、块 ID、脚注定义全部由运行时算出。

remember(subject="Dave", kind="person",
         fact="Dave moved to Pudong.",
         sources=["D1:1"])

落到磁盘上：

# Dave

Dave moved to Pudong.[^e-4265834607] ^3e926ade

[^e-4265834607]: Time: `2023-05-08`; Sources: [D1:1](../../sources/D1.md#d1-1)

路径由 _subject_path() 按类别定：person → topics/people/、project → topics/projects/、relationship → topics/relationships/、theme → topics/themes/。这一条顺带解决了一个隐蔽问题：同一个人以前会被模型写成 people/caroline.md 和 relationship/caroline-and-melanie.md 两份，现在同名必然同文件。

3.2 收窄工具面

写入阶段只保留 remember 一个工具。shell 和整文件写入是弱模型用来犯错的余地，不是用来干活的能力。

原来由模型决定现在
拼出 topics/people/xxx.md交主体名和类别，路径由规则定
手写 ^new-block-x、脚注定义、来源链接运行时生成
先 ls / read 摸清有哪些主体已有主体清单直接写进任务
手握 shell / write_file / edit_file写入阶段只有 remember
检索第一轮自己发起搜索先跑确定性检索，结果进初始上下文

重组阶段仍然需要改写既有文件，那里保留 write_file / edit_file / read_file / shell——按 stage 区分，写入和重组本来就是两件事。

3.3 拒绝要说清原因

修复指引从"整轮结束后的修复轮"移到工具返回值本身，模型犯错的当下就看得到。并补齐了三条原本缺失的错误类型：

错误补上的指引
memory block ID required新段落以 ^new-block-<name> 结尾，接在引用之后
unused footnote definition每条定义都要有段落引用它，否则删掉定义
old_text appears 0 times先读文件再原样抄，省略号形式的引用匹配不到任何东西

另外，重复失败按"同一文件 + 同一类错误"计数而不是参数完全相同——模型重试时通常会把措辞改一点，精确匹配的计数器永远不会触发。第二次起会明确告诉它这是第几次同样的尝试。

§4 检索：先查再问

4.1 索引按版本缓存

每次 Search 都在重建 BM25 与嵌入索引。18 秒的请求里模型只占 2–3 秒，其余全是建索引。改成按工作区版本号缓存后，同样形状的请求（2 轮、2.2k token、1 次工具调用）从 16.2 秒降到 2.5 秒。

缓存键包含版本号，所以每次 Add 都会作废它。我的基准是先跑完所有 Add 再跑 Search，缓存全命中；如果平台交替调用，命中率会大幅下降。这一条尚未验证，见 §7。

4.2 返回读到的原文

原来只返回模型最后那段转述，中位 1 条、39 个字符——调用方拿着一句话去回答问题。现在返回三层，去重后按 top_k 截断：

  1. 模型的报告

    它认为哪些内容相关，这是判断，排在最前。

  2. 它实际读到的原文

    RetrievalToolState.evidence 累积了每次工具调用的非空输出，那就是记忆本身。按来源工具过滤掉目录列表和被拒命令。

  3. 本地索引兜底

    模型什么都没找到时返回最接近的若干条。索引是本地的，这一层不花任何模型调用。空手返回必然是 0 分。

并且把这次确定性检索提到最前面执行，结果直接放进模型的初始上下文。"先按查询词搜一次"从来不是判断，是每次都要做的动作——预先做掉之后，多数请求模型一轮就能回答，工具调用降到 0 次。

§5 用量与轨迹

两处记录是这一轮所有判断的基础，此前都不存在。

  • 每请求一行用量日志：轮数、输入输出 token、停止原因、返回条数、工具调用次数。
  • OpenAI agent 的轨迹：每轮调了什么工具、参数是什么、返回了什么。Claude 那条路径一直有记录，OpenAI 这条没有，于是"跑满 20 轮做完了工作"和"跑满 20 轮原地打转"在日志里长得一模一样。

计时器一开始起在索引构建之后，日志报 1.3 秒而调用方实际等了 17 秒。已改为覆盖整个请求——写监控要先确认它量的是不是调用方感受到的那个数。

§7 检索用词面排序,不用嵌入

服务默认 SCRIPTORIUM_SEARCH_TOOLS=bm25。这不是偏好,是量出来的。

工作区fused(BM25+嵌入)bm25(纯词面)
LoCoMo 4 会话,20 题,端到端判分0.550.60
BEAM 100K × 5,97 题,金标词覆盖51.2%50.8%
Search p90 延迟12.3 s3.7 s
镜像体积2.4 GB744 MB

准确率上两者是平的——判分那 0.05 是一道题,BEAM 上的 0.4 个百分点更是噪声。差别在别处:延迟差 3.3 倍,镜像差 1.7 GB,而且纯词面不需要把嵌入模型烤进镜像,也就不依赖评测机能连上 Hugging Face。

项目里 fused 曾是默认,依据是一次「一个融合工具 vs 分开的两个工具」的对比(40 题里 34 对 30)。那次两边都开着嵌入,赢的是工具的打包方式——模型不必自己发两次搜索再手动合并。嵌入这一半值不值,在此之前没有测过。上表是第一份直接证据。

fused 仍然可用,改一个环境变量即可,届时需要一并安装 sentence-transformers。服务在启动时检查当前配置对应的后端,缺件直接拒绝启动。

§8 未完成

按影响排序，前两条决定 4.9 秒这个数在真实评测里成不成立

  1. 索引缓存在交替调用下是否有效。缓存键含工作区版本号，每次 Add 都会作废。基准是先 Add 后 Search 的最好情况，平台的实际调用顺序未验证。
  2. 并发未验证。平台会开 64 个 Add、256 个 Search；本地最多测过 6 个线程。索引构建那把锁是全局的，高并发下第一波会全部串行等待。
  3. 规模未验证。只跑过一个对话的前 4 个会话、20 道题；完整对话是 19 个会话、199 道题。
  4. 记忆只增不整理。服务刻意不在请求内跑重组以免超时，长对话下 topic 文件会一直变长，退化成单个巨大文件。
  5. remember 只能追加。用户改口或事实更新时两条记录并存，knowledge_update 类问题会受影响。
  6. 代码未提交，仍在工作树中。
