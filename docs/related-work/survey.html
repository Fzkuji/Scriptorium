§1 Scope and Taxonomy

Agent memory system 将跨会话历史保存为可持续更新的外部状态，并在后续任务中选择相关信息。本文采用两个主要分析维度：Memory Organization 研究保存什么以及记忆条目之间如何组织；Retrieval Methods 研究如何根据当前 query 定位相关条目。

维度核心问题主要分类
Memory Organization记忆单元保存什么？不同单元如何关联？Representation Unit、Organization Structure、Organization Operations
Retrieval Methods系统使用什么匹配机制定位候选证据？Exact Lexical（grep）、Sparse Lexical（BM25）、Dense Semantic（Embedding）

训练方式、存储基础设施和产品形态是与上述两个维度正交的系统属性。LLM 可以理解问题、改写检索词、选择工具、判断候选并决定是否继续检索，但这种控制方式不构成第四种底层检索方法。目录、timeline、links 和 source references 是建立在 Memory Organization 上的结构化访问方式，也不与三种匹配机制并列。

§2 Memory Organization

2.1 Representation Unit

Representation Unit 描述系统写入一个 memory item 时保存的内容。一个系统可以同时保存多种表示。

类型定义代表系统主要取舍
Raw Turn / Episode保存原始对话、交互记录或文档片段MemGPT / Letta、E-mem保留细节，但存储量和检索范围较大
Summary将一段历史压缩为较短文本MemoryBank、LangMem、MemoryOS降低上下文成本，但可能删除日期、数字和原始措辞
Atomic Fact / Note将信息拆成独立事实或笔记单元A-Mem、SimpleMem便于更新和匹配，但拆分过程可能丢失上下文关系
Event保存带时间、参与者和上下文的事件描述TiMem、ES-Mem适合跨会话和时间推理，但依赖事件抽取质量
Entity / Relation将内容表示为实体、属性和关系Zep / Graphiti、Mem0支持关系查询，但结构化抽取可能省略原始语境
Hybrid Representation同时维护事实、事件、摘要、实体或原文Hindsight、AdaMem覆盖多种信息需求，但同步和维护成本更高

2.2 Organization Structure

Organization Structure 描述 memory items 之间的排列和关联方式。这些结构不是互斥类别，完整系统可以组合多种结构。

结构组织方式代表系统主要取舍
Flat / Sequential按时间或写入顺序保存列表、日志或 archival memoryMemGPT / Letta、MemoryBank写入简单；规模扩大后依赖额外检索器
Hierarchical / Tree按抽象层级、时间粒度或生命周期构建多级结构MemWalker、TiMem、MemoryOS、MemOS支持由粗到细的访问，但层级构建错误会影响后续定位
Graph-based通过实体、事件、语义或因果边连接记忆节点Zep、Hindsight、Mnemis支持跨节点关系推理，但需要构图和图更新
File / Wiki-based使用文件、目录、Markdown 页面和链接组织文本HORMA、ByteRover、Karpathy LLM Wiki内容可读且可直接检查；效果依赖命名、层级和文件维护
Multi-view为同一记忆集合维护两个或更多组织视图AdaMem、FluxMem、Hindsight支持不同查询需求，但必须处理跨视图一致性

2.3 Organization Operations

Memory Organization 不只决定初始表示，也包括记忆随新信息变化时执行的操作。

操作作用代表方法
Add / Admit判断新信息是否进入长期记忆A-MAC、MemRouter
Update / Invalidate处理事实纠正、信息冲突和旧记录失效Mem0、DeltaMem
Merge / Consolidate合并重复或相近内容，形成较高层表示SimpleMem、TiMem、LightMem
Link / Reorganize增加关联、调整归属或重建结构A-Mem、Mnemis、Hindsight
Forget / Prune按时间、效用或容量限制删除仍然有效但不再保留的内容MemoryBank、H-Mem、SimpleMem

§3 Retrieval Methods

对于文本形式的外部记忆，底层候选生成分为三类：Exact Lexical Retrieval、Sparse Lexical Retrieval 和 Dense Semantic Retrieval。三者都可以由固定程序调用，也可以由 LLM 生成 query、检查结果并反复调用；LLM 是否参与属于控制与路由方式，不作为独立的 retrieval method。

3.1 Exact Lexical Retrieval

Exact Lexical Retrieval 直接扫描原始文本，不需要预先为 memory items 建立另一套检索表示。典型工具是 grep：它执行精确字符串或正则表达式匹配，并返回原文件中的匹配位置。该方法不需要额外模型，也不需要维护文本到索引条目的映射；文本发生变化后可以立即搜索。

它适合姓名、编号、日期、专有名词和已知原句，但不能自动处理同义改写。搜索成本随文本规模增长，结果本身也不提供完整的相关性排序。

3.2 Sparse Lexical Retrieval

Sparse Lexical Retrieval 仍以词项匹配为基础，但预先将 memory corpus 切分为带 ID 的检索单元，并维护 tokenization、倒排索引、词频、文档长度和全局词项统计。BM25 是典型方法：它根据 query term 的出现频率、区分度和文档长度计算相关性分数，再返回排序后的候选。

BM25 不需要 learned model，但需要在写入、修改或删除文本后同步更新稀疏索引。Mem0、Zep 等系统将 BM25 作为混合检索信号。

3.3 Dense Semantic Retrieval

Dense Semantic Retrieval 使用额外的 Embedding 模型，将 memory items 和 query 编码为稠密向量，并通过向量相似度返回 top-k 候选。系统需要保存原始文本、memory ID 和对应向量，并在文本变化后重新编码和更新向量索引。

该方法适合同义表达、概念相关和自然语言改写，但效果依赖 Embedding 模型、memory 切分、索引粒度、相似度函数和 top-k。MemoryBank、A-Mem、LangMem、Mem0 和 Zep 均使用这一方法；Hybrid Retrieval 可以进一步组合 BM25 与 dense retrieval。

相同的 grep、BM25 或 Embedding 可以由固定流水线调用，也可以由 Agent 自主调用。LLM 负责 query 理解、工具选择、候选判断和停止决策；底层匹配方法本身不因此改变。

§5 Orthogonal Design Choices

5.1 Training

Training-free systems 依赖 prompt、规则和现成模型完成记忆操作。另一类工作通过 supervised fine-tuning、RL、PPO 或 GRPO 学习写入、检索或维护策略，例如 Memory-R1、MemReader、DeltaMem、AtomMem 和 HORMA。训练方式影响部署成本和策略适应性，但不决定系统采用哪种 memory organization 或 retrieval method。

5.2 Infrastructure

基础设施用途常见系统
Plain text / File system保存可直接读取和编辑的文本、目录及链接MemGPT、HORMA、ByteRover
Vector index / Vector DB保存 embedding 并执行相似度搜索MemoryBank、A-Mem、Mem0、LangMem
Graph store / Graph DB保存实体、事件和关系并执行图查询Zep、Hindsight、Mnemis
Hybrid backend组合文本、向量和图结构Mem0、Zep、MemOS

§6 Evaluation

最终回答准确率同时受到 memory construction、retrieval、answerer 和 judge 的影响。不同论文使用不同模型、prompt、数据子集和评分器时，单个百分比不能直接用于方法排序。除 answer accuracy 外，还应分别报告 evidence recall、temporal reasoning、multi-hop reasoning、abstention、检索 token、延迟、工具调用数和 memory construction cost。
