Research Execution Plan

Scriptorium 研究执行计划

记录项目当前进度、剩余研究任务、依赖关系和执行顺序；不按论文结构组织。

updated 2026-08-06 · current architecture baseline reset

当前近期执行细则：LongMemEval-S Smoke 与 S4/S8 选择计划。该文档记录 Memory 组件边界、查询 mask 消融、批次级 checkpoint/恢复语义、冻结配置、multi-session 机械 smoke、复用 A-S8 的两题配对设计、六类型 smoke 和 30-sample 预实验。

1. 当前进度

项目已经完成当前 Scriptorium 架构的主要代码实现，但该架构尚未产生可用于论文主表的正式实验产物。旧 V8/V11/NativeMem 的 Memory、答案和分数只作为历史设计参考；除非原始产物、代码身份和协议身份均可审计，否则不得计入当前架构进度或正式比较。

已经完成

  • Scriptorium 的 Source Memory、Topical View、Temporal View、source references、文件导航和运行时约束已经实现。
  • Writer、Manager、verification 和 query 已迁移到隔离的 Claude Agent SDK runtime；旧运行中的 DSML 文本化工具调用不再出现。
  • BM25、Embedding、baseline adapters、统一评测、token accounting、统计分析和审计工具已经具备。
  • 当前代码已与 GitHub main 对齐到提交 459e367；Python 3.12 WSL 环境与项目依赖已经安装，conversation runner 可以正常启动。
  • LoCoMo、LongMemEval oracle、LongMemEval-S 与 BEAM 100K/500K/1M 数据已经恢复；LoCoMo、LongMemEval-S 和 BEAM-100K 与项目冻结数据哈希一致。
  • DeepSeek V4 Flash via PackyAPI 与 GPT-4o-mini via OpenRouter 已完成最小连通性和模型身份验证；两个服务均返回预期模型。
  • 旧实验分析证明项目历史上运行过 V8/V10/V11 与 model-scaling 实验，但当前 clone 不包含其原始 Memory/result 目录，因此这些数字不视为当前正式资产。

尚未完成

  • 当前 Scriptorium 架构尚未运行任何正式 build。目前没有通过审计的 Conv-50 development Memory，也没有 LoCoMo full-10 或 LongMemEval-S 当前架构 Memory。
  • 当前架构尚未生成正式 answers 或 judge 结果。旧版本的 90.84%、78.05%、87.00% 等数字只能作为历史参考，不能放入当前主表。
  • 当前 SDK 架构的 Writer 输入上限、session batch、局部整理频率、verification 频率和成本上限尚未在 development conversation 上冻结。
  • Scriptorium 与主要 baseline 在同一 answerer、judge、题集和资源统计口径下的完整比较。
  • Topical View、Temporal View 和 Source Resolution 的正式全量消融。
  • 同一连续记忆在不同历史增长位置上的任务质量与成本评估。
  • 正式结果的统计区间、judge sensitivity、人工核验和失败归因。

当前门禁与阻塞

  • LoCoMo evaluator 的实际 SHA-256 与 AGENTS.md 锁定值不一致。在锁冲突被用户明确解决前，可以做 build-only、结构审计和非 LoCoMo 诊断，但禁止任何 LoCoMo scoring。
  • 正式配置 JSON 尚未落盘；模型价格、Writer token cap、预算上限和输出目录仍需在 development run 后冻结。
  • 历史 Memory 未随 clone 分发，也不符合当前 source archive、evidence annotation 与 stable block ID 架构，不能直接迁移成当前正式结果。

2. 剩余研究任务

任务 A：统一协议整体比较

在 LoCoMo 和 LongMemEval-S 上完成 Scriptorium、Full Context、BM25、Mem0 和 Graphiti 的统一比较。所有可控条件使用相同问题集合、answerer、judge 和成本统计范围。异构论文自报结果只作为外部参考，不参与统一排名。

输出：完整任务结果，以及构建调用、构建 token、查询调用、查询 token、延迟和存储规模。

任务 B：多视图与来源组件实验

使用 R203 的四个条件：dual view + source、topic only + source、timeline only + source、dual view without source。所有条件复用冻结的记忆内容和 source references，只改变可访问视图或原文回读能力。

执行设计：采用 决策 AB-01：冻结完整构建、查询时遮罩；正式消融前必须通过 full-profile 等价性门禁，并将结果限定解释为 query-time access ablation。

输出：整体 QA、按问题类型结果、source recall、工具调用和成本差异。

任务 C：增量增长实验

使用 R403 在 10%、25%、50% 和 100% 历史位置评估同一连续记忆。每个 checkpoint 只允许访问当时已经到达的历史，不能访问未来信息。

输出：QA、旧事实保持、更新事实、source reachability、构建成本、查询成本和存储增长。

任务 D：可靠性分析

对任务 A–C 的最终产物执行 conversation-clustered bootstrap、paired tests、judge sensitivity、100 题人工核验和基于 trace 的失败归因。这些分析复用已生成答案，不重新修改方法。

3. 执行顺序

  1. 协议与身份门禁。记录当前 Git commit、数据哈希、builder/answerer/judge 模型、endpoint、prompt 和预算口径；在任何 LoCoMo scoring 前单独解决 evaluator 哈希锁冲突。
  2. LongMemEval-S multi-session development。先按 专项 smoke 计划完成一个 A-S8 机械 smoke，再复用它并新增 A-S4、B-S4 和 B-S8，以两组同题配对选择 S4 或 S8。
  3. 冻结任务 A 配置。只有 development Memory 结构审计通过、批次级恢复有效且 S4/S8 决策完成，才冻结唯一正式 config；development 结果不进入主表。
  4. 完成任务 A 的正式全量运行。先构建 Scriptorium 正式 Memory，再在统一题集、answerer、judge 和资源口径下完成 Scriptorium、Full Context、BM25、Mem0 与 Graphiti 比较。
  5. 完成任务 B。整体系统结果确定后，使用 R203 判断多视图和 Source Resolution 是否产生可测作用。
  6. 完成任务 C。使用已经冻结的完整方法评估持续增长，避免在增长实验中继续改变基础配置。
  7. 完成任务 D 与结果审计。答案和 trace 固定后计算统计区间、judge sensitivity、人工一致性和失败类型，并核对每个论文结论是否由正式产物支持。

5. 结果决策

  • 如果 Scriptorium 在统一协议下没有质量优势，继续报告文件状态、证据保留和成本结果，但不宣称普遍性能领先。
  • 如果移除某个视图没有稳定影响，该视图保留为系统接口，不写成已经验证的效果来源。
  • 如果 Source Resolution 产生稳定收益，保留 source-grounded memory 作为主要设计；否则检查其成本是否仍有保留价值。
  • 如果增长过程中 QA 通过明显增加查询调用才能保持稳定，必须同时报告质量和成本变化。
  • 如果不同 judge 的结论不一致，以人工核验和逐题分析限定结论范围。

6. 暂不执行的任务

  • R207 固定路径对照：只有需要研究“自主组织是否优于固定组织”时执行。
  • R301 organizer–retriever interaction：只有需要研究组织者与检索者的模型对齐时执行。
  • Recent Memory 与 Core Memory benchmark：没有对应任务前只保留为系统能力。
  • 独立 BM25、Embedding 和 grep 工具消融：这些工具不是当前研究的独立贡献。
  • BEAM-1M：不阻塞 LoCoMo、LongMemEval-S 和核心组件实验。

7. 研究完成标准

  • 统一整体比较的每个方法都有完整配置、问题级答案、judge 记录和成本记录。
  • R203 能够说明 Topic、Timeline 和 Source Resolution 的实际作用或无效结果。
  • R403 覆盖 10%–100% 历史增长，并保存每个 checkpoint 的任务与成本结果。
  • 主要比较具有统计区间、judge sensitivity 和人工核验。
  • 所有结果都能从保存的 manifest、answer、trace 和 usage 产物重新计算。
