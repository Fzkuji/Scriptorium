LongMemEval-S Execution Note

LongMemEval-S Smoke 与 S4/S8 选择计划

用最少的重复构建验证当前架构、比较 multi-session 条件下的 S4 与 S8，并逐步扩展到六类型和 30-sample 预实验。

created 2026-08-06 · current architecture · pre-formal

1. 目标与边界

  • 第一优先级是确认当前 Scriptorium 架构能完成一个完整 LongMemEval-S sample 的构建和回答，而不是立即生成可发表分数。
  • 优先检查历史上表现偏弱的 multi-session 类型，并以同题配对方式选择 S4 或 S8。
  • 每个 sample 必须使用完整 haystack history；不得截取部分 session 作为质量 smoke。
  • 旧 V10 的 S8 结果只用于提出候选参数，不视为当前架构证据。

2. 组件与模块边界

一次成功构建不是单个摘要文件，而是一份带身份、来源和派生关系的组件化 Memory bundle。各组件按以下边界保存：

组件性质生成/维护者复用与拆分规则
Source权威、append-only 的完整原始交互Runtime 自动归档所有条件共享的证据底座；禁止 LLM 覆盖；可在查询时屏蔽 Source 回查但不得删除原始产物
Topic权威、可编辑的主题语义状态Writer / Manager独立冻结；可通过视图 mask 做 topic-only 或隐藏 Topic
Core权威、独立维护的持续目标与约束Writer / Manager独立冻结；主比较保持一致，不与 S4/S8 一起变化
Timeline带日期的派生文本视图Runtime 从已提交状态重建可重建、可独立屏蔽；不重新调用 builder
RecentTopic 最近 50 个 block 的有界派生视图Runtime可重建、可屏蔽；不是独立构建条件
RelationsMarkdown links、backlinks 与 source referencesRuntime 校验和物化随冻结 Memory 保存；消融时可限制访问，不能破坏原始引用
grep / file access直接文本访问接口Query Navigator 选择无独立索引；属于查询时可访问工具
BM25稀疏检索索引Runtime 从可见文本重建可删除和重建；不作为重新构建 Memory 的理由
Embedding可选稠密检索索引Runtime 从可见文本重建模型与索引身份单独记录；本 smoke 不要求启用
Selected Evidence / Answer查询阶段产物GPT answerer与 Memory 分开保存；可对同一冻结 Memory 重新回答或重新 judge

构建边界：DeepSeek 只参与 Source 归档后的 Topic/Core 语义写入和管理；Timeline、Recent、Relations、BM25 与 Embedding 不应产生额外 builder 调用。S4 与 S8 的差异只允许改变 Writer 每次接收的完整 session 数。

3. 运行前门禁

  1. 构建、查询回答和 judge 分开配置：DeepSeek 负责构建，冻结的 GPT answerer 负责查询回答，GPT-4o-mini 只负责需要评分的阶段。
  2. 批次级 checkpoint 已实现：每个 Writer batch 成功提交后保存已处理 session/source cursor、Memory revision、调用量和 usage；恢复时从下一个未完成批次继续。
  3. 冻结数据哈希、代码提交、Writer/Manager prompt hash、模型身份、S 值、verification/local-management 周期和预算。
  4. 只有数据、代码、prompt、模型和构建配置身份完全一致时，已有 Memory 才允许复用。

当前实现：LongMemEval runner 同时具备 item 级和 Writer batch 级 checkpoint。运行中的 build-checkpoint.json 记录当前批次、session 范围、source turn 数和已提交进度；每次工具调用追加到 writer-live-*.jsonl，模型消息轮次写入配套 progress 文件，失败时另存 writer-failure-*.json。因此可以在批次结束前发现重复错误，也能从最后一个已提交批次继续。

跨平台执行约定：模型可见的命令工具始终使用 POSIX Bash 语法。shell_backend=auto 在 Linux 保留原生旧行为、在 Windows 选择 Git Bash；正式 Windows smoke 显式冻结为 posix-bash，native 只用于历史复现。所有 POSIX shell 输出按 UTF-8 解码并以替换方式容错，避免中文 Windows 的 GBK 解码线程中断。文件读取、BM25 和 Embedding 是 Python 内部工具，不经过系统 shell。

4. Checkpoint 与恢复语义

4.1 四层状态

层级建议文件记录内容恢复行为
Runmanifest.json数据/代码/prompt/模型/config hash、计划样本、开始与结束时间身份不一致时停止，不自动覆盖旧 run
Itemitems/<id>/checkpoint.jsonnormalize、build、retrieve/answer、judge 的阶段状态和产物路径已完成阶段跳过；只继续未完成阶段
Build batchitems/<id>/build-checkpoint.json固定 batch plan、已完成 batch、session/source cursor、Memory revision、usage 与验证状态从下一未完成 batch 继续，最多重做一个未提交 batch
Query/Judgeanswer.json / judge.json问题、Memory hash、tool trace、selected evidence、答案、judge 原始响应和 usageMemory/answer 身份匹配时分别复用，不触发 builder

4.2 每个 Writer batch 的提交顺序

  1. 从已冻结的 batch plan 读取当前完整 session；先由 Runtime 将其完整归档到 staged Source。
  2. Writer 修改 staged Topic/Core；Runtime 校验 block ID、source references、路径和事务约束。
  3. Runtime 原子提交 Source/Topic/Core，并重建 Timeline、Recent 与 Relations，得到新的 Memory revision。
  4. 按冻结周期执行 verification；需要时只修复当前已提交范围，再生成新 revision。
  5. 最后原子写入 build checkpoint，记录 batch 完成、cursor、revision、调用和 usage。

如果模型调用或 staged 校验失败，丢弃未提交 stage，只重试当前 batch。如果 Memory 已提交但进程在 checkpoint 写入前中断，恢复程序必须通过 transaction receipt、source cursor 和 revision 对账，识别该 batch 已提交，禁止重复写入。

4.3 恢复前校验

  • dataset item、session 顺序、source IDs 和 batch plan hash 必须一致。
  • builder model、Writer/Manager protocol hash、S 值、verification/local-management 周期必须一致。
  • checkpoint 声明的 Memory revision、已归档 source cursor 和磁盘实际状态必须一致。
  • 任何不一致都应停止并保留现场，不能自动删除或把旧 Memory 标记为成功。

6. 分阶段执行

阶段 1：机械 smoke（一个 multi-session sample）

选择一个约 48 个 session 的完整 multi-session sample，记为样本 A；使用 S8 完成构建、检索和回答，暂不调用 judge。

  • 检查 Source 是否覆盖全部输入消息，Topic/Timeline 引用是否可回查，Core/Recent/Relations 是否正常。
  • 检查每批 checkpoint、故障恢复、调用量、token、耗时、成本和磁盘规模。
  • 成功后冻结并保留 A-S8 Memory、回答和完整 manifest，后续不得重复构建。

阶段 2：两个 multi-session sample 的 S4/S8 配对

再选择一个规模接近的完整 multi-session sample，记为样本 B。复用阶段 1 的 A-S8，只新增三次构建：

样本S4S8本阶段动作
A新增构建复用阶段 1形成第一组配对
B新增构建新增构建形成第二组配对

四个条件使用相同 GPT answerer 生成答案，再统一交给 GPT-4o-mini judge。除 session batch 外，模型、prompt、verification、management、检索接口和预算必须一致。

阶段 3：六类型效果 smoke

冻结 S4 或 S8 后，每类选择一个完整 sample：single-session-user、single-session-assistant、single-session-preference、multi-session、temporal-reasoning 和 knowledge-update。

multi-session 条件直接复用阶段 2 中相同样本、相同获胜配置的 Memory 和答案，因此通常只需新增另外五类构建。六个答案统一评分，用于发现类型性失败，不作为正式 benchmark 分数。

阶段 4：30-sample 预实验

每类 5 个 sample，共 30 个。只有阶段 3 没有出现系统性结构、引用或恢复错误时才进入本阶段；完全匹配冻结身份的阶段 2/3 产物可以计入并复用。30 个 sample 通过后再进入 LongMemEval-S 全 500 题。

7. 构建复用与查询时消融

决策 AB-01：冻结完整构建，查询时遮罩。所有主消融先使用同一份完整构建并冻结的 Memory；实验条件只改变查询时可见视图、Source 回查权限或检索工具，不物理删除主 Memory，也不重新调用 builder。S4/S8 因改变构建过程，必须分别构建，不属于遮罩消融。

  • Memory 是按 dataset item 和构建条件隔离的；A-S4 与 A-S8 是两份不同构建，不允许互相覆盖。
  • 回答失败或 judge 尚未执行时，复用已经完成且校验通过的 Memory，不重新调用 builder。
  • BM25 与 Embedding 属于可重建索引，不作为重复调用 builder 的理由。
  • 任何构建配置或 Writer/Manager 语义变化都会产生新的构建身份；旧 Memory 保留供审计，但不与新条件混用。

后续组件实验优先对同一份冻结完整 Memory 使用只读访问 mask，不重新调用 DeepSeek：

条件可访问视图Source 回查是否重建 Memory
dual view + sourceTopic + Timeline允许否，完整冻结条件
topic only + sourceTopic允许否，只改变查询 mask
timeline only + sourceTimeline允许否，只改变查询 mask
dual view without sourceTopic + Timeline禁止否，保留 Source 文件但查询不可见

这类实验测量的是“查询时能否访问组件”的作用；如果要回答“从构建开始就没有该组件会怎样改变其他 Memory”，必须另做结构性消融并重新构建，不能用 mask 结果替代。

7.1 固定实施流程

  1. 按完整架构构建 Source、Topic、Core，并由 Runtime 生成 Timeline、Recent 和 Relations；保存完整构建 manifest 与 Memory hash。
  2. 将完整 Memory 标记为冻结。后续遮罩、回答、judge、索引重建和投影清理均不得改变其内容哈希。
  3. 每个消融条件生成独立的 access-profile.json 和只读查询投影；保持允许文件的相对目录、文件名、block ID 与链接路径不变。
  4. 文件投影和工具层同时执行 allowlist。被屏蔽的 Source 不能通过 shell、grep、BM25、Embedding、链接解析或直接路径绕过。
  5. BM25/Embedding 只针对当前投影中的可见文本建立，并以 Memory hash + profile hash + index/model identity 缓存。
  6. 答案、tool trace、selected evidence、usage 和 judge 均记录 Memory hash 与 profile hash；同一条件可重试回答，但不得触发 DeepSeek 重建。

7.2 Full-profile 等价性门禁

在正式使用遮罩消融前，必须证明“全部开启的查询投影”与直接读取原始完整 Memory 等价：

  • 可见文件列表和文件内容哈希一致；相对路径、Markdown links、block IDs 和 source references 解析一致。
  • 相同 query 下 grep 与 BM25 候选一致；启用 Embedding 时模型、索引输入和候选一致。
  • 工具 schema、权限和返回内容一致；固定模型设置下 tool trace 不出现由投影层造成的新差异。
  • 生成和使用投影前后，原始 Memory hash 不变。

若等价性门禁失败，完整版继续直接读取原始 Memory；不得为了统一接口而让完整版经过可能改变行为的投影层。

7.3 效率与结果解释

  • 投影生成、索引重建/加载时间单独记录为 condition setup，不计入 DeepSeek 构建成本，也不得隐藏在查询模型耗时中。
  • 遮罩消融可以支持“查询依赖某组件”的结论，不能支持“构建时不需要/需要某组件”的结论。
  • 如果某一遮罩产生稳定、关键的质量差异，再选择少量样本补做从构建阶段移除组件的结构性消融。
  • 结构性消融必须产生新的 build identity、Memory 和成本记录，不能覆盖或冒充遮罩条件。

7.4 后续实施检查单

  • 本条件是否只改变一个预先声明的访问变量？
  • 是否复用了完全相同的冻结 Memory，且没有发生 builder 调用？
  • 被遮罩组件是否同时从文件可见性、工具权限和检索索引中消失？
  • 回答与 judge 是否绑定正确的 Memory/profile hash？
  • 原始 Memory 在实验前后的内容哈希是否相同？
  • 论文表述是否明确写成 query-time access ablation，而非 build-time structural ablation？

8. S4 / S8 决策规则

  1. 首先比较两题的 judge 正确性和 gold answer-session 可达性。
  2. 若一方在两题上稳定更好，选择该配置。
  3. 若结果打平，依次比较 source coverage、引用有效性、构建错误、恢复稳定性、调用量、token 和 wall time；质量门禁满足后优先选择成本更低者。
  4. 若两题结论冲突或差异无法解释，再增加两个 multi-session sample 做配对，不直接扩大到 30 个。

9. 每次运行必须保存的产物与当前状态

  • 不可覆盖的 Source、Topic、Timeline、Core、Recent、Relations 以及可重建检索索引的身份信息。
  • batch plan、批次级 checkpoint、Memory revision、完成/失败状态和恢复记录。
  • 构建、verification、management、查询回答和 judge 的独立调用及 usage 统计。
  • 数据、代码、prompt、模型、配置与 Memory 内容哈希。
  • 检索 tool trace、selected evidence、Source 回查结果、答案和后续 judge 原始响应。
