# LongMemEval-S 检索后作答优化交接文档

## 1. 文档目的

本文档记录 LongMemEval-S 错误链中 S 类（检索后作答错误）的当前判断、建议改进路径、实施边界和验证方案，供后续开发、实验和复盘使用。

本文只讨论影响回答效果的查询期链路，不修改记忆构建语义、Writer、已有 checkpoint、原始实验结果或 Judge。本文提出的方案目前属于待实施设计，不能表述为已经修复或已经取得指标提升。

相关结果分析见：

- `docs/research/LONGMEMEVAL-ERROR-CHAIN-FINDINGS-20260814.html`
- `docs/research/LONGMEMEVAL-LOCOMO-RESULTS-20260813.html`
- `docs/research/LONGMEMEVAL-WSL-EXPERIMENT-FINDINGS.md`

## 2. 当前结论

现有审计表明，S 类的共同特征不是目标事实完全没有进入记忆，也不主要是检索工具完全没有命中，而是关键证据进入检索上下文之后，系统仍可能在以下环节失败：

1. 没有完整保留和组织多轮检索得到的候选证据；
2. 重复、冲突、新旧状态和原始来源之间的关系不清晰；
3. 模型过早锁定第一次取得的候选，后续强证据没有充分改变结论；
4. 多项事实已经取得，但范围筛选、聚合、数值语义或时间解释仍然错误；
5. 证据不足时过度推断，或证据充分时仍然拒答；
6. 检索与最终作答由同一个 Agent 连续完成，缺少稳定的中间证据状态。

因此，当前优化重点应表述为“查询期证据管理和检索后推理”，而不是笼统地称为提高 Retriever 召回率。

记忆构建并非绝对没有错误，但从当前效果审计看，它不是 S 类的主要矛盾。不建议为了处理 S 类而重新构建全部记忆。

## 3. S 类问题类型

### 3.1 候选枚举、聚合与数值语义

常见表现：

- 多个实体、多笔记录或多个事件没有完整列出；
- 相同事实从不同组件返回后被重复纳入；
- 未先限定问题范围便开始计算；
- 把总额、差额、剩余量、次数或对象数量混为一谈；
- 已取得全部数字，但求和、差值、最大值或门槛判断错误。

这里同时包含“证据组织”和“计算语义”两层问题。证据账本可以改善前者，但不能自动保证后者正确。

### 3.2 偏好归纳

常见表现：

- 把一次行为视为长期稳定偏好；
- 没有同时比较支持证据和反证；
- 没有区分明确表态与间接行为；
- 忽略偏好随时间变化或不同场景的适用范围；
- 较早偏好持续主导答案，较新证据没有被正确吸收。

纯程序无法可靠判断这些语义关系，需要保留 LLM 判断，但应让判断过程具有可追踪的证据结构。

### 3.3 时间、动作语义与窗口

常见表现：

- 已取得日期，但使用了错误的参照时间；
- 时间窗口边界或包含关系错误；
- 混淆谈话时间、事件发生时间和状态有效时间；
- 混淆计划、尝试、进行中、完成或取消；
- 多个候选事件中选错符合时间条件的事件。

程序账本可保存和排序时间元数据，但不会自动理解所有相对时间和动作状态。

### 3.4 证据充分性与拒答

常见表现：

- 只有间接或不完整证据时给出确定答案；
- 忽略问题中的限定词；
- 证据能够支持有限结论，却输出了范围更大的结论；
- 已有足够证据时仍然过度保守地拒答。

账本可以展示当前实际取得了哪些证据，但是否足以支持答案仍然需要语义判断。

### 3.5 新旧状态迁移

常见表现：

- 新事实已经召回，但最终答案仍沿用旧状态；
- 把补充信息误认为覆盖，或把真正的更正误认为并列事实；
- 更新只适用于特定场景，却被错误扩展到全局；
- 后取得的原始来源没有取代较早摘要中的不准确信息。

单纯按时间排序不等于完成更新判断。后续需要区分覆盖、补充、冲突和无关关系。

> 注意：以上类型是错误机制，不保证彼此互斥。同一个样本可能同时涉及时间窗口和数值聚合。统计实验必须同时报告唯一样本数和机制命中数，不能直接把机制数量相加当作修复样本数。

## 4. 不建议采用的方案

### 4.1 不固定执行所有 Retriever

不建议每道题都无条件执行 BM25、Embedding、实体、Timeline 和 Source 检索。原因包括：

- 增加模型调用、工具调用和端到端延迟；
- 引入大量与简单问题无关的候选；
- 扩大上下文，可能进一步稀释关键证据；
- 削弱当前 Agent 根据问题复杂度自主选择检索路径的优势。

应继续让 LLM 决定是否以及如何扩展检索。

### 4.2 不为 benchmark 题型编写专用答案规则

不建议针对 LongMemEval 的题型硬编码偏好、时间、数值或拒答模板，也不应利用已知 gold 或错误样本建立规则。这会产生针对 benchmark 的过拟合和刷分风险。

允许实施的只能是可迁移到普通问答的通用机制，例如证据去重、来源追踪、时间字段标准化和结论—证据一致性检查。

### 4.3 不因 S 类重新构建全部记忆

S 类定义本身是关键证据已进入查询链路后仍然答错。除非新的审计证明确有 Writer 漏写，否则不应把 S 类问题转化为全量记忆重建。

## 5. 建议总体架构

保留当前 LLM 自主检索，只在工具结果和 Agent 推理之间加入轻量 Evidence Ledger（证据账本）：

```text
问题 + Core + Recent + 组件目录
                ↓
       LLM 自主选择检索工具
                ↓
            工具返回结果
                ↓
       程序去重并更新证据账本
                ↓
 LLM 查看已知证据、来源、时间与未决缺口
                ↓
      继续自主检索或生成最终答案
```

该方案不增加固定 Retriever，不改变记忆数据，不要求额外启动一个 LLM。第一阶段的主要变化是把已经取得的结果组织成稳定、精简、可审计的中间状态。

## 6. 第一阶段：纯程序证据账本

### 6.1 目标

第一阶段只处理客观元数据，不要求程序推断证据语义，也不增加模型调用。

建议字段：

```json
{
  "evidence": [
    {
      "evidence_id": "stable-id",
      "source_ref": "component/path/reference",
      "component": "core|recent|timeline|relations|topics|sources",
      "retrieval_method": "initial|bm25|embedding|file_read|source_verify",
      "retrieval_round": 1,
      "retrieval_score": null,
      "event_time": null,
      "conversation_time": null,
      "content_hash": "...",
      "verified_from_source": false
    }
  ]
}
```

### 6.2 程序负责的工作

- 根据稳定引用或内容哈希去重；
- 保留证据的组件、文件和原始引用；
- 标记证据由哪种工具、哪一轮检索取得；
- 记录工具已有的检索分数；
- 保存事件时间、会话时间等已有字段；
- 标记是否已经读取或验证原始 Source；
- 将 Source 验证结果关联回对应摘要；
- 控制账本长度，避免同一内容在上下文中重复出现；
- 不覆盖原始工具轨迹，账本只是派生状态。

### 6.3 第一阶段主要覆盖的问题类型

- 候选枚举中的漏看、重复和来源混淆；
- 多轮检索后结果散乱、早期结果锚定；
- 时间证据没有按可比较形式呈现；
- 新旧证据虽然都出现，但后取得证据不够显眼；
- Source 验证结果与原记忆摘要脱节；
- 上下文中重复片段过多导致的证据稀释。

### 6.4 第一阶段不能解决的问题

- 不能判断一条事实支持还是反驳某个答案；
- 不能判断新事实是否真正取代旧事实；
- 不能判断一次行为是否构成稳定偏好；
- 不能保证范围筛选、求和或差值正确；
- 不能判断证据是否足以给出确定答案；
- 不能修复 LLM 本身对问题语义的误解。

## 7. 第二阶段：由现有 Agent 补充语义关系

只有第一阶段消融表明“证据组织改善但仍有明显语义关系错误”时，才进入第二阶段。

第二阶段仍不新增一次 LLM 调用，而是在现有 Agent 阅读工具结果、决定下一步时，要求其顺手输出少量结构化更新。

建议字段：

```json
{
  "evidence_updates": [
    {
      "evidence_id": "stable-id",
      "role": "supports|conflicts|context|unknown",
      "target_claim": "short internal hypothesis",
      "state_relation": "current|superseded|supplements|unrelated|unknown"
    }
  ],
  "open_questions": [
    "short unresolved evidence gap"
  ],
  "current_hypothesis": null
}
```

程序仅负责验证枚举值、引用存在性、去重、版本和合并。语义内容由当前 Agent 判断，并必须满足：

- 所有标签绑定具体 evidence id；
- 不允许无来源的结论进入账本；
- 新证据出现后允许修改旧标签；
- 无法确认时使用 `unknown`，不能强制二分；
- 最终回答仍能访问最关键的原始证据片段；
- 账本错误不能覆盖或删除原始检索记录。

### 7.1 第二阶段主要覆盖的问题类型

- 偏好归纳中的支持证据、反证和稳定性比较；
- 新旧状态中的覆盖、补充和冲突判断；
- 多个候选结论与证据之间的对应关系；
- 已知证据与尚未确认缺口的显式区分；
- 检索过程中结论变化无法追踪的问题。

### 7.2 第二阶段风险

- LLM 可能在首次标注时判断错误，并把错误固化在账本中；
- 结构化输出增加少量 token 和格式处理复杂度；
- 账本过长会重新产生上下文负担；
- 如果把 `superseded` 等关系写成硬规则，可能误处理场景依赖事实。

因此第二阶段必须是可关闭的实验开关，且应保留原始工具结果作为最终事实来源。

## 8. 后续可选增强

这些能力不应与第一版账本同时一次性实现。只有消融实验确认对应类型仍然失败时，再分别考虑。

### 8.1 结构化聚合区

适用于候选枚举完成后仍发生范围或数值错误的情况。建议让 Agent 在内部显式生成：

```text
纳入项
排除项及原因
计算表达式
单位和范围
计算结果
```

这是通用推理过程，不应包含 LongMemEval 专用题型规则。

### 8.2 时间标准化区

适用于账本已经提供全部时间证据，但相对时间、窗口和动作状态仍然错误的情况。建议显式区分：

- 参照时间；
- 事件时间；
- 会话时间；
- 状态有效区间；
- 区间端点是否包含；
- 计划、开始、进行、完成、取消等动作状态。

现有 time view 应作为输入，而不是被替换。首先需要通过实验判断失败来自 time view 信息不足，还是 Agent 没有正确使用已有信息。

### 8.3 证据充分性字段

适用于证据组织后仍然过度回答或过度拒答的情况。可要求 Agent 区分：

- 直接证据；
- 间接证据；
- 推断；
- 关键缺口；
- 当前结论适用范围。

该机制必须保持通用，不根据 benchmark 的答案分布决定何时拒答。

## 9. 与 Mem0 思路的关系

Mem0 当前公开方案强调语义、关键词和实体等多信号检索、融合排序、时间重排和较小的稳定候选集合。其优势更偏向在第一次检索时形成集中候选。

本项目不建议直接复制其“固定多路检索”路径，因为现有系统已经具有丰富的六组件记忆、Source 验证和 Agent 自主补查能力。更适合借鉴的是“稳定候选状态”这一思想：

- Mem0 通过较固定的融合排名稳定候选；
- 本项目通过轻量证据账本稳定 Agent 已经取得的候选；
- 保留自主检索优势，同时减少多轮工具结果散乱造成的错误。

Mem0 公布成绩的回答模型、提示词和 Judge 口径不一定与本实验相同，不能直接把指标差距归因于 Retriever。

## 10. 实施边界

### 10.1 不修改

- Writer 和记忆构建 prompt；
- checkpoint 语义；
- Core、Recent、Timeline、Relations、Topics 和 Sources 的存储格式；
- 原始检索轨迹和失败证据；
- LongMemEval gold 或 Judge；
- LoCoMo evaluator 及其锁定文件。

### 10.2 应提供的开关

建议至少提供以下独立开关，默认关闭，避免改变现有正式结果的复现语义：

```text
retrieval.evidence_ledger.enabled
retrieval.evidence_ledger.semantic_labels
retrieval.evidence_ledger.max_entries
retrieval.evidence_ledger.include_verified_excerpt
```

纯程序账本和语义标签必须可以独立启用，以便进行消融。

### 10.3 审计要求

- 账本是派生数据，不是新的事实来源；
- 每项必须能追溯到原始 source ref；
- 记录创建、更新和被替换的轮次；
- 不在日志中泄露完整问题、答案、gold 或记忆正文；
- 账本格式异常时应回退到现有检索流程，而不是导致答案任务失败；
- 不删除或覆盖已有实验输出。

## 11. 验证方案

### 11.1 基本原则

- 使用已经冻结的完整记忆，不重新构建；
- 使用同一回答模型、相同问题和相同工具集合；
- 首先做离线路径审计，不自动调用付费 Judge；
- Judge 仅在离线结果讨论后由用户明确授权；
- 不使用 gold 引导检索或修改运行时行为。

### 11.2 建议消融组

| 组别 | 检索方式 | 证据账本 | 语义标签 | 其他增强 |
|---|---|---|---|---|
| A | 当前自主检索 | 无 | 无 | 无 |
| B | 当前自主检索 | 纯程序 | 无 | 无 |
| C | 当前自主检索 | 纯程序 | 现有 Agent 补充 | 无 |
| D | 当前自主检索 | 纯程序 | 视结果决定 | 仅加入被证明必要的单项增强 |

### 11.3 按问题类型选样

抽样应覆盖：

- 候选枚举和聚合；
- 偏好归纳；
- 时间、动作和窗口；
- 证据充分性与拒答；
- 新旧状态迁移。

不需要在交接文档中绑定具体 dataset index。实验记录另行保存样本清单和冻结输入哈希。

### 11.4 观察指标

除最终正确率外，应记录：

- 工具调用次数；
- 输入和输出 token；
- 端到端耗时；
- 取得的唯一证据数；
- 重复证据压缩比例；
- Source 验证是否成功关联回摘要；
- 最终答案使用的证据是否在账本中；
- 是否存在关键证据已取得但未被最终结论使用；
- 语义标签是否在新证据出现后正确更新；
- 格式错误和回退次数。

### 11.5 成功判据

第一阶段可视为成功，需要同时满足：

1. 相同或更少的检索调用下，证据重复和上下文长度下降；
2. 候选组织、来源关联和新旧证据可追踪性改善；
3. 对至少一种主要 S 问题类型产生稳定改善；
4. 不显著损害原本正确的样本；
5. 不依赖 LongMemEval 专用规则。

如果第一阶段已经获得足够改善，应停止扩展，不应为了完整设计而继续增加语义和验证机制。

## 12. 决策与停止条件

### 12.1 进入第二阶段的条件

只有同时满足以下条件才增加语义标签：

- 第一阶段证明证据账本能够稳定运行；
- 失败样本已经取得并组织了完整证据；
- 剩余错误集中在支持/反证、偏好稳定性或新旧状态关系；
- 增加语义字段的收益预计高于 token 和复杂度成本。

### 12.2 增加计算或时间模块的条件

- 候选集合已经完整且无重复；
- 错误明确发生在计算、范围或时间解释；
- 相同机制在多个普通问题上重复出现；
- 方案能够表述为通用能力，而非 benchmark 专用修补。

### 12.3 放弃账本方案的条件

出现以下情况之一，应停止或回退：

- 上下文和 token 成本明显增加但正确性没有改善；
- 账本语义标签比原始推理更不稳定；
- 正确样本因过度结构化而退化；
- Agent 工具调用显著增加；
- 账本与原始 source ref 频繁失配；
- 改善只能通过针对已知 benchmark 题型的规则取得。

## 13. 推荐执行顺序

1. 在不改变现有运行语义的独立分支实现纯程序 Evidence Ledger；
2. 为去重、来源关联、轮次更新、Source 验证关联和长度上限编写单元测试；
3. 使用冻结记忆执行 A/B 消融；
4. 按问题类型分析改善和退化，不只看总正确率；
5. 与用户讨论离线结果；
6. 仅在第一阶段不足且证据支持时实施语义标签；
7. 计算、时间和充分性增强分别独立评估，不能一次全部叠加；
8. 只有用户明确批准后才进行付费 Judge 复评；
9. 确认收益后再决定是否合入默认运行配置。

## 14. 交接结论

当前最小、风险最低的优化不是增加固定 Retriever，也不是重建记忆，而是为现有自主检索增加一层轻量、可追溯的证据账本。

第一版由程序维护来源、时间、轮次、去重和验证状态，主要解决检索结果散乱、重复、来源脱节和上下文稀释。它不能替代语义推理、计算、时间解释或充分性判断。

只有第一版验证有效后，才考虑让同一个 Agent 补充支持、冲突、新旧状态和未决缺口等语义标签。再后续的计算、时间或充分性机制必须由剩余错误类型驱动，逐项实施和消融。

截至本文创建时，以上方案尚未实施，因此不能宣称已经解决任何 S 类错误或提升 LongMemEval 指标。
