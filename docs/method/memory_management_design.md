# NativeMem 记忆管理设计（运行逻辑）

> 本文档只定**运行逻辑**——模型该按什么规则去组织、整理、检索记忆。**不写死任何针对特定 benchmark 的目录结构**。目录长什么样，由模型按下面的通用规则自己决定；换任何数据、任何领域，同一套规则都成立。
>
> 先定逻辑，后谈实现（哪步是 prompt、哪步是代码，见文末"实现待议"，本轮不决定）。
> 版本：draft-1，2026-07-04。取代对结构的一切硬编码假设。

---

## 0. 一句话原则

**记忆是模型自己维护的一份"结构化笔记"。模型遵循一套固定的"记笔记的习惯"（通用规则），而不是遵循我们规定的具体目录。** 好的记忆系统 = 好的记笔记习惯 + 持续的自我整理，而不是一次性把东西堆进去。

这套习惯要满足两个硬约束：
- **通用**：规则不提任何具体主题/文件名，换个领域照样能用。
- **自洽**：存、整理、取三个环节用**同一套**结构认知——存的时候按"以后会怎么找"来放，取的时候就能按同样的逻辑找到（这就是 RAM，Retrieval-Aligned Memorization 的本意）。

---

## 1. 当前问题（为什么要重设计）

实测（v5-qwen s0）暴露的病根，全部指向**没有一套自我整理规则**：

- 一个实体 60+ 个主题标题，且大量近义未合并：`mental health career` / `mental health work` / `mental health counseling` 是同一件事拆成三个；`art` / `art appreciation` / `mural` / `poetry` 散成四个。
- 同名标题重复：`## art` 在一个文件里出现 3 次。
- 根因：**逐段处理、每段只看当前内容、看不到已有结构**——模型处理第 30 段时不知道 `## art` 已经存在，就又建一个。

结构一乱，检索就没法"按结构导航"，只能退回关键词硬搜（grep），于是又出"措辞对不上找不到"。**所以根子在构建，不在检索。**

## 2. 记忆管理的三个环节 + 通用规则

### 环节 A：写入（把新对话变成记忆）

模型每拿到一段新对话，按固定习惯做三步：

1. **先看已有结构，再决定放哪**（治重复的关键）。
   写入前，模型必须先了解"现在这份笔记里已经有什么"——已有哪些实体、每个实体下已有哪些主题。**优先把新信息归到已存在的主题下；只有确实是新主题，才新建。**
   → 通用规则，不涉及具体主题名。它逼模型复用已有结构，而不是无脑新建。

2. **提炼成一条自包含的事实，并保证不漏**（核心，见 §2.1 完整性）。
   - 代词换成具体实体名；专有名词、数字、精确限定词一字不丢；
   - 相对时间用会话日期锚定（"上周"→"某日的前一周"），不硬算、不瞎编精度。

3. **每条记忆一次存全三样东西**（构建只做一次，检索时再分档取用，见 §2.2）。
   一条完整的记忆条目包含：
   - **提炼句**（distilled）——模型总结的自包含事实；
   - **原文引用**（verbatim）——复制的原始对话原句；
   - **精确来源链接**——指到原始对话的**具体哪一行/哪一句**（不是只到 chunk，要到行级），便于精确回溯。

4. **放到"以后会去找它"的位置**（RAM）。
   模型问自己："以后有人问起这件事，我会去哪个实体、哪个主题下翻？" 就放那里。存放逻辑 = 检索逻辑，两者对齐。

> 写入环节的通用习惯：**先复用、后新建；粒度自包含；一次存全（提炼+原文+行级链接）；按检索路径存放。** 没有一句是针对某个 benchmark 的。

#### §2.1 怎么保证提炼不漏信息（完整性）

各家都靠"软提醒"防漏，我们在软提醒之外再加一层"硬校验"——这是我们存了原文、能用代码对照才做得到的，别人做不到。

**软机制（加进提炼 prompt，借鉴各家）：**
- **逐条处理**（学 LightMem）：按顺序处理每条消息，别因为"看着不重要"就跳过；每条提炼事实标注它来自原文第几行（行号绑定），漏了哪行、序号就断了。
- **自检 + 数量下限**（学 Mem0）：输出前把整段再扫一遍；一段多话题的对话通常产出多条事实，若只抽出很少条，重读——很可能漏了。专门防"第一话题支配"（把开头抽得细、后面当废话）。
- **拿不准就抽**（学 Mem0）：宁可多抽，重复交给整理环节去重；漏抽的代价远大于冗余。

**硬校验（我们独有，代码做，确定性）：**
- 提炼完之后，代码把**原文里出现的专有名词/数字**和**提炼出的事实**对一遍；原文里有、提炼里没覆盖的关键实体，标出来**让模型补抽**。
- 这一步不靠模型自觉，是确定性地"发现漏了什么"。既补上漏抽（正好打之前诊断的 single-hop 专有名词丢失短板），也是我们相对纯 prompt 方法的一个机制优势。

#### §2.2 两种情况：不用原文 vs 用原文

我们的记忆分两种情况跑，也是两种口径：

**情况一（不用原文，正规口径）——答题只靠我们加工出来的记忆，不碰任何原始对话。**
- 这是**跟别人对标的口径**：Mem0/LightMem/SeCom 都是这样——加工完原文就丢了，检索答题只看加工后的内容。我们也只看加工后的记忆，才是苹果对苹果的公平比较。**论文主结果用这一档。**
- 关键问题：**这一档里"怎么加工"是我们要重点设计和实验的开放问题**，见 §2.3。因为加工方式（总结 / 删废话 / 别的）直接决定这一档的成败——SeCom 已经证明"纯总结丢细节、效果差"，所以我们不能想当然地就用总结。

**情况二（用原文）——加工后的记忆 + 原文一起，答不出时回原文兜底。**
- 这是**我们独有的加分项**：因为我们的记忆里除了加工后的内容，还留着原文引用和精确到行的来源链接。加工不够时能回原文核对/补答。
- 纯 embedding 方法结构上做不到这个（它们加工完就丢了原文）。这一档展示"有原文兜底能补回多少加工时丢的信息"。

**实现上两种共用同一份构建产物**（构建时该存的都存：加工后的记忆 + 原文引用 + 行级链接），检索时用代码控制"给不给模型看原文"来区分两种情况。**构建是"一次建全两种共用"还是"分开各建"效果更好，先不定死，做实验看结果。**

> 必须真正做到"情况一看不到任何原文"：raw 原始对话存档要排除在检索可见范围外，加工后的记忆里也不能夹带整句原文，否则就不是"不用原文"了，口径不干净（已发现的漏洞）。

#### §2.3 「不用原文」这一档：怎么加工是核心开放问题（要设计+实验）

这是我们方法最需要想清楚、也最有研究价值的一点。加工原始对话有一个**强度光谱**，从"几乎不动"到"彻底改写"：

| 加工方式 | 做什么 | 谁在用 | 已知结论 |
|---|---|---|---|
| **照抄** | 一字不动 | 我们 baseline | 不丢细节但啰嗦、废话多、可检索性差（70.4） |
| **删废话** | 删掉语气词/冗余，保留原词原序，不改写不概括（LLMLingua-2 那种） | SeCom / LightMem | 既不丢细节又变干净——SeCom 证明**比总结好** |
| **总结成事实句** | 换说法、概括成自包含事实 | 我们 v5、Mem0 | 可检索性好但**丢细节**（SeCom 实证纯总结最差；我们 v5 也印证 66.4） |

**要研究的问题**：在"不用原文"这一档里，到底哪种加工最好？以及——
1. **总结 vs 删废话**：SeCom 证明"删废话 > 总结"，但它没有我们的"结构化 + 导航"。在我们这套框架里，是不是也是删废话更稳？还是总结配上好结构反而能赢？
2. **有没有中间地带**：能不能"该总结的总结、该保原词的保原词"——比如事件/时间用总结（好检索），专有名词/细节保原词（不丢）？
3. **加工强度随什么变**：随模型能力（强模型能吃更狠的总结？）、随问题类型（细节题要保原词、聚合题要总结）？

> 这一档的加工方式**由我们自己设计并用实验定**，不照搬任何一家。这正好接上"总结粒度/频率是文献空白"那个点——**"不用原文时，加工到什么强度最优"本身就是一个没人干净研究过的问题**，是我们的设计空间也是潜在贡献点。

#### §2.4 我们的加工方式：三者结合（分层加工）

三种加工各有取舍，坏处都来自"对整段内容一刀切用同一强度"。我们的设计**不是三选一，而是按内容类型分层用不同强度**——让一条记忆同时拿到"好搜"和"不丢细节"。

**核心思路：一条记忆 = 总结的骨架 + 嵌进去的原词细节。**

具体分两层加工：

**① 骨架层（总结强度）—— 把"发生了什么、什么时候"总结成一句清晰的话。**
- 事件、动作、时间、因果这类**关系性信息**，用总结：换成清晰措辞、代词消解、相对时间锚定。
- 这层负责"好搜好导航"——问"她什么时候去支持组"，这句清晰的骨架最容易被命中。

**② 细节层（照抄强度）—— 骨架里凡涉及专有名词/数字/具体限定词，一律用原词，不许换、不许概括。**
- 专有名词（人名、书名、地名、品牌）、数字、精确限定词（"带狗脸的杯子"里的"狗脸"）→ **原样嵌进骨架句**。
- 这层负责"不丢细节"——之前 Sweden 被总结成"祖国"、Becoming Nicole 被总结成"一本书"的坑，就是这层堵死的。

**举例**（一条记忆同时含两层）：
- 原话：`"嗯，我昨天其实去了一个 LGBTQ 支持小组，读了本叫 Becoming Nicole 的书，特别震撼"`
- 我们加工出的记忆：`[2023-05-08前一天] Caroline 去了 LGBTQ 支持小组，读了《Becoming Nicole》，觉得很震撼`
  - 骨架（总结）：`Caroline 去了…读了…觉得很震撼`（清晰、好搜、代词消解、时间锚定）
  - 细节（原词）：`LGBTQ 支持小组`、`《Becoming Nicole》` 原样保留，没被概括成"一个小组""一本书"
  - 删掉的废话：`嗯`、`其实`、`一个`、`本叫`——这就顺带做了"删废话"。

**怎么保证细节层不被总结吞掉（关键，用代码兜底）**：
- 靠 prompt 要求模型"专有名词/数字原样保留"是**软**的，弱模型会漏（已实测）。
- 所以加一步**确定性代码校验**（§2.1 的硬校验）：提炼完，代码扫原文里的专有名词/数字，凡没出现在骨架句里的，标出来让模型补回。这把"细节层"从软约束变成硬保证。

**这套设计同时收编了三者的优点、避开缺点**：
- 有总结的"好搜"（骨架层）
- 有照抄/删废话的"不丢细节"（细节层原词 + 删废话）
- 避开纯总结的"丢细节"（细节层堵死）、避开纯照抄的"啰嗦难搜"（骨架清晰、废话删了）

**待实验确认的旋钮**（这就是 §2.3 那个开放问题的具体形态）：
- 骨架总结到多"狠"（保留多少上下文）随模型能力/问题类型怎么调；
- 哪些算"必须保原词的细节"（专名+数字是底线，限定词/情感词要不要也保）；
- 这套"分层加工" vs 纯删废话（SeCom 那种）vs 纯总结，在同口径下谁高——这是我们要跑的核心对比实验。

### 环节 B：整理（维持结构不腐化）

写入是增量的，长期必然产生冗余和碎片。所以需要一个**周期性的自我整理**动作（像人隔一阵子重整笔记本），按固定规则收拾：

1. **合并近义主题**：一个实体下若有多个语义高度重叠的主题，合并成一个（`mental health career/work/counseling` → 一个）。
2. **消除重复**：同一事实存了多份的，去重；同名标题出现多次的，并成一个。
3. **拆分过载**：一个主题/文件长到难以浏览时，按子主题拆开，留一个索引指向子项。
4. **该建目录就建目录**：一个实体的主题多到一个文件装不下时，允许模型把主题拆成子文件/子目录——**但拆成什么样由模型按"是否更好导航"自行决定，我们不规定**。

> 整理环节的通用习惯：**合并近义、去重、按需拆分。** 触发时机可以是"每处理 N 段"或"结构指标超标"（具体见实现待议）。关键是**整理是一个显式、独立的环节，不是指望写入时顺手做好**——写入时模型看不到全局，整理时才能看到全局做归并。

### 环节 C：检索（答题时找记忆）

**LLM 是主检索器，结构导航和词法搜索是它可选择的工具。** 系统不把查询固定成某一种 top-k 流水线，也不使用 Embedding 模型替 LLM 决定相关性。

LLM 可在同一上下文中交替使用：

1. **目录与 `cat`**：主题或人物路径明确时，直接阅读相关 topic 和兄弟文件；
2. **`grep`**：查专名、原句、编号和已知精确短语；
3. **BM25**：路径不明确、问题包含多个概念、或 `grep` 未命中时，对 topic 事件做关键词排序；
4. **timeline**：处理日期、先后、持续时间和状态变化；
5. **`read_original`**：已找到 source refs 后，核验原词、日期、指代和冲突。

BM25 只返回候选，不自动进入回答上下文；LLM 可以改写查询、换工具或继续搜索。原始对话不能被通用 shell 全文搜索，只能经 `read_original` 受限访问。

> 检索环节的通用习惯：**先判断当前最缺哪类信息，再选择成本最低的合适工具；候选不等于证据，最终答案必须经过文件内容或原文核验。** 检索质量同时取决于记忆结构、词法召回和 LLM 的工具编排能力。

## 3. 三个环节如何咬合（整体运行流程）

```
对话流
  │  每段对话
  ▼
[A 写入]  看已有结构 → 提炼自包含事实 → 按检索路径放到已有/新主题
  │
  │  每处理若干段 / 或结构超标时触发
  ▼
[B 整理]  看全局 → 合并近义主题、去重、按需拆分
  │
  ▼  （得到一份结构整齐、主题不重复的记忆）
  │
[C 检索]  LLM 判断信息缺口 → 自选目录/grep/BM25/timeline → read_original 核验 → 回答
```

**关键设计点**：A 是"局部、增量、看不到全局"，所以它做不好归并——这是 B 存在的理由。**过去的错误是指望 A 在写入时顺手把结构管好，结果它看不到全局，越堆越乱。把"归并整理"独立成 B，才是治本。**

## 4. 这套逻辑为什么通用（不是给 benchmark 定制）

- 全程没有一句规定"该有 art 主题""该按人建文件"——实体、主题、目录层次全由模型按"复用优先、近义合并、按需拆分、便于导航"这几条**通用启发式**自己长出来。
- 换成客服对话、病历、项目文档，同一套规则（先复用后新建、周期整理、结构导航）照样成立。
- 这正是我们方法相对向量库的立论：**记忆是一份模型自己维护、人也能读的结构化笔记，靠好的记笔记习惯而非固定 schema。**

## 5. 运行细节（三个关键点的推荐做法）

下面三点是这套逻辑成败所在，给出推荐方案。原则贯穿始终：**能用确定性代码保证的（索引、精确去重、日期、拆分阈值），交给代码；只有需要"语义判断"的（这两个主题是不是一回事、这条事实归哪个主题），才交给模型。**

### 5.1 让模型"看到已有结构"——两级视图，代码只给顶层，模型自己往下翻

**核心：记忆系统对外只有一个固定入口（记忆根目录）。入口底下长什么样——有没有 `people/`、按人还是按主题分、几层深——全部由模型自组织，代码一个路径都不预设、不写死。** 代码可以把"当前结构现状"作为上下文呈现给模型，但绝不接管"放哪、建什么"的结构决策。

上下文控制用**两级视图**（记忆长大后会有很多文件，不能全塞进 prompt）：

- **默认只给顶层目录（粗视图）**：记忆根目录下有哪些文件/文件夹，**不展开任何文件内部**。这个视图永远小（一个 `ls` 的结果），给得起。
- **往下翻是模型自己的事（细视图按需）**：模型觉得该往某个文件放/找，就自己用 bash（`grep '^##' Caroline.md` 看该文件有哪些主题、`ls 子目录/` 进去看）。探索多深、看哪些文件，全是模型的决定，代码不预先展开、不控制它看多少。

→ 上下文天然可控：顶层视图恒小；细节只在模型主动探索时才进上下文，且只进它关心的那一两个文件。代码的职责收缩到最小——**给顶层视图、提供 bash 工具、屏蔽 raw、保证内容完整性（原文层+行级链接），不碰结构决策**。

**写入与检索用同一套动作**（都是"给顶层视图 → 模型自己往下翻 → 定位”）：
- 写入：模型翻着找"这条该放哪个已有位置"，放进去或新建。
- 检索：模型翻着找"这个问题的答案在哪个位置"，取回来。

存的时候模型怎么翻着放，取的时候就怎么翻着找，两边结构认知一致，自然对得上——这就是 RAM（存取自洽）落到实处。过去 v5/v6 把"放哪"用代码硬编码（`people/{person}.md`）接管了，模型的自组织能力从没被用上，结构永远是"一人一大文件、主题全挤一起"，检索也只能退回 grep 硬搜。改回"模型自组织 + 两级视图"是治本。

### 5.2 整理的触发与执行——代码触发，模型执行语义合并

- **触发（代码判定）**：不是每段都整理。按确定性指标触发，二选一或都用：
  - 每处理完 **一个 session** 触发一次（session 是自然的批次边界）；
  - 或结构指标超标触发（某实体主题数 > 阈值、或检测到重复标题）。
- **执行（代码做机械活 + 模型做语义活）**：
  1. **精确重复 → 代码删**：完全相同的条目、同名标题，代码直接去重合并，不劳模型。
  2. **近义主题合并 → 代码给候选、模型定夺**：代码使用简单词重叠、BM25 或共同实体筛选候选对（如 `mental health career` / `mental health work`），**只把候选对喂给模型判断“是否该合并、合并后叫什么”**。这里不使用 Embedding；代码只缩小范围，最终语义判断仍由模型完成。
  3. **过载拆分 → 代码判阈值、模型执行**：主题/文件超过行数阈值时，代码标记，模型按子主题拆开并留索引。

→ 这样"整理"不是一次昂贵的全局重写，而是"代码找问题点 → 模型只处理这些点"。

### 5.3 检索屏蔽 raw 原文（必修的口径漏洞）

- raw 原始对话存档**不能进检索范围**——否则模型能直接翻原文找答案，等于把 memory 任务退化成在原文里做 RAG，评测口径不干净（这是已发现的实测漏洞）。
- 实现：检索的工作目录只暴露**整理好的记忆**（提炼条目 + 其双层原文引用），把 raw/ 目录排除在检索可见范围外。原文核对只通过记忆条目里那份 `> "..."` 引用，不通过 raw 全文。

### 5.4 小结：谁做什么

| 环节 | 代码负责（确定性） | 模型负责（语义判断 + 结构决策） |
|---|---|---|
| 写入 | 给顶层目录视图、日期规范化、写入原文层+行级链接、屏蔽 raw | 提炼事实、**自己往下翻探索结构、决定放哪个位置/建什么文件/主题** |
| 整理 | 触发判定、找精确重复、算主题相似度给候选、判拆分阈值 | 判断候选主题是否合并、合并命名、**按需建/拆目录（拆成什么样模型定）** |
| 检索 | 提供目录、grep、BM25、timeline 与受限 source resolver；维护词法索引并屏蔽 raw/sources 全文搜索 | **判断调用哪个工具、改写什么查询、读哪些候选、何时核验原文与停止** |

> 关键红线：**代码给"当前结构现状"作为上下文是可以的（顶层视图），但不控制结构**——放哪、建什么、按什么分、几层深，从写入到整理全是模型基于"入口下已有什么"自己决定。代码退回到"给视图 + 给工具 + 保内容完整性"。上下文用两级视图控制（默认给顶层、模型按需往下翻），既让模型看得到已有结构（防重复），又不因记忆变大而爆上下文。

---

## 6. 一句话小结

**给模型一套通用的“记笔记习惯”和一组无学习检索工具，让它自己组织记忆，并在目录、grep、BM25、时间线和原文解析之间持续决策；不为任何 benchmark 写死目录或固定检索流水线。**
