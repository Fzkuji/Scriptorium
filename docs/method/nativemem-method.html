Current Method Specification

NativeMem: File-Native, Source-Grounded Multi-View Memory

NativeMem 将 Source、Topic、Timeline、Recent、Core 和索引关系组织为一个文件式记忆状态。Topic 是可编辑的主要语义状态；Timeline、Recent 与索引由 Runtime 从 Topic 确定性生成。LLM 负责语义选择和组织，Runtime 负责身份、校验、同步与事务。

updated 2026-08-01 · V11 benchmark implementation + target online contract

§1 Method Overview

CONTRIBUTION 01

File-native memory substrate

权威记忆保存在可读、可版本化的文本文件中。Source 只追加，Topic 可编辑，Core 独立维护；BM25 与 Embedding 只建立可重建的辅助索引，不保存唯一事实。

CONTRIBUTION 02

Source-grounded multi-view memory

系统在完整 Source Memory 之上维护 Topic、Timeline、Recent、Core 和跨视图索引。不同视图承担不同访问需求，同时通过稳定 memory ID 与 source references 保持一致。

方法按记忆生命周期组织：原始交互先进入 Source；Writer 从新增 Source 构建或更新 Topic；Runtime 由 Topic 生成 Timeline、Recent 和索引；Core 由 LLM 单独维护；查询 Agent 再按问题选择文件访问、grep、BM25 或 Embedding。下文分别说明状态结构、构建、管理和查询。

§2 Memory Architecture

session t 的状态定义为 M_t = (S_t, T_t, D_t, R_t, C_t, G_t)。其中 S_t 是不可变证据，T_t 是可编辑的主要语义状态，C_t 是独立维护的常驻上下文；D_t、R_t 和 G_t 均可由权威状态重建。

2.1 Source Memory

Source 保存完整消息和外部文档定位信息，是所有派生内容的证据边界。对话来源使用 provider 提供的稳定 thread_id 与 message_id；文件来源使用路径及页码、章节或行号。Runtime 可以生成便于阅读的显示标题，但显示标题不替代稳定定位符。Source 只追加，不因 Topic 修改、记忆纠错或视图重建而覆盖。

2.2 Topic Memory and Memory Unit

一个记忆单元表示一条可以独立追踪来源和时间的事实或事件，但它不要求在 Topic 文件中独占一行。Topic 是由 LLM 自由编辑的 Markdown；记忆单元通过正文后的 footnote ID 与来源定义保持身份。JSON 只用于首次写入和 Runtime 内部 reconciliation，不是权威存储格式。

字段语义决定者系统处理在文件中的表示
memory_id无Runtime 生成并保持稳定[^mem_7f31c2]
contentWriter、Manager 或 ReconcilerRuntime 解析对应正文片段自然语言正文
whenWriter 或 ReconcilerRuntime 校验并生成 Timelinefootnote 定义中的日期；未知时为 undated
source_refsWriter 或 Reconciler 从候选来源中选择Runtime 解析、校验并转换稳定链接footnote 定义中的一个或多个链接
topic_pathLLM 通过创建或移动文件决定Runtime 从实际路径读取topics/personal/residence.md
headingLLM 通过编辑标题决定Runtime 从 Markdown 层级读取## 居住经历

Topic 使用“目录—文件—标题—正文”的自由 Markdown 结构。LLM 可以调整段落和章节，不需要将正文限制为逐条 JSON。Runtime 只要求可追踪的事实正文具有 memory ID 和有效来源。

一个段落被解析为交替出现的正文片段和引用组。每个引用组对应从段落开头或上一个引用组之后开始、到当前引用组之前结束的正文；连续的多个 ID 共同对应同一段正文。标题、代码块和 footnote 定义不参与正文解析。

2.3 Derived Views

Timeline、Recent 和 Relations 不保存独立事实。Timeline 按 when 提供时间入口；Recent 保留最近创建的 50 个 memory ID；Relations 包括 Topic 与 Timeline 的链接、source backlinks、查询时 structure map，以及 BM25/Embedding 索引。Runtime 在 Topic 提交后统一重建受影响部分，因此 Writer 不需要分别调用 Timeline 或 Recent 写入工具。

2.4 Core Memory

Core 保存每次交互都需要提供的稳定信息，例如长期任务约束和持续偏好。它不是 Topic 的派生副本，也不进入 Recent FIFO。LLM 负责决定 Core 的保留、改写和删除；Runtime 限制其总量为 2K tokens、校验可追踪引用，并与同一事务中的其他文件一起提交。Core 中可由 Source 或 Topic 支持的事实必须保留对应引用。

2.5 Authority and Dependencies

Provider messages / files
        ↓ Runtime append
Source S ──→ Writer / Reconciler ──→ Topic T
                                      ├──→ Timeline D
                                      ├──→ Recent R
                                      └──→ Relations G
Source S + Topic T ──→ LLM Manager ──→ Core C

事实追踪方向始终回到 Source。Topic 和 Core 是需要保存的语义状态；Timeline、Recent、链接、structure map、BM25 与 Embedding 索引均可删除后重建。session cursor、scheduler 和 Git 状态属于 Runtime，不写入记忆正文。

§3 Memory Construction

构建只处理 session cursor 之后的新增 Source。Writer 做一次语义决策，Runtime 完成所有确定性物化，避免对每个视图分别调用 LLM。

阶段输入LLM 职责Runtime 职责输出
1. Source ingestionprovider 消息与外部文件无保留 provider ID、路径和定位信息；只追加 Source；推进前不修改 cursor新增 Source 区间
2. Candidate preparation新增 Source、已有引用、本轮读取文件无生成临时 source handles、Topic inventory 和局部上下文有限候选集合
3. Semantic writing候选集合与相关 Topic决定 content、when、source_refs、topic_path、heading；必要时更新 Core提供结构化写入接口写入 proposal
4. Materialization写入 proposal无校验来源，生成 memory ID，写入 Topic，生成 Timeline、Recent 与 Relationsstaged memory state
5. Commit完整 staged state无检查覆盖与一致性，原子安装，创建 Git commit，成功后更新 cursor新的 M_t

Writer 的内部 proposal 可以是结构化 JSON，但权威输出仍是 Markdown：

{
  "content": "用户于 2026-07-20 搬到上海。",
  "when": "2026-07-20",
  "source_refs": ["src_17", "src_41"],
  "topic_path": "personal/residence.md",
  "heading": "居住经历"
}

src_17 等 handle 仅在当前事务内存在。Runtime 将其解析为稳定 message ID 或文件定位；文件显示标题依次取文档元数据标题、正文标题和原始文件名，不由 LLM 生成。

§4 Memory Management

管理以 Topic 修改为中心。LLM 只编辑需要语义判断的 Topic 或 Core；Runtime 检测变更、决定是否需要 Reconciler，并同步所有派生视图。

4.1 Direct Topic Editing and Reconciliation

LLM 可以直接修改 Topic Markdown，不需要调用逐字段 update_memory。文件写入结束后，Runtime 比较修改前后的正文与 ID：

检测到的修改是否调用 Reconciler后续处理
路径、标题、顺序、空白或格式改变，正文与 ID 不变否Runtime 按现有 ID 确定性同步
已有 ID 的正文改变是判断同一记忆改写或新增事实
新增无 ID 正文，或发生拆分、合并是识别正文边界，匹配旧 ID，为新事实分配新 ID
旧 ID 消失，或日期、来源改变是区分移动、合并、显式纠错和非法隐式删除
新事实没有有效候选来源是拒绝事务并恢复修改前状态

Reconciler 由 Runtime 自动调用，只读取修改章节、受影响旧记忆和有限候选来源。它返回旧 ID 匹配、新记忆正文、日期和 source handles；Runtime 再校验引文是否真实、正文是否存在、旧 ID 是否被合法处理。正在编辑的 LLM 不需要生成 reconciliation JSON，也不需要额外调用工具。

4.3 Fact Evolution, Ordering, and Transactions

现实状态变化与事实纠错分开处理。状态变化新增一条带时间和来源的记忆；事实纠错显式删除或替换错误派生项，但保留 Source。普通改写不能通过删除 footnote 隐式删除记忆。

顺序定义
Source保持原始消息数组、JSONL 或时间戳顺序，不受 Topic 编辑影响
Topic按引用在 Markdown 中的出现顺序，由 LLM 决定
Timeline按事件时间排序；同一时间按主要 Source 时间，再按 memory_id
Recent按首次创建顺序维护；普通改写和移动不改变顺序，新 ID 追加到尾部

一次管理事务依次执行：暂存 Topic/Core 修改、检测差异、必要时 reconciliation、校验 memory ID 与 source coverage、重建 Timeline/Recent/Relations、原子安装、创建 Git commit、最后更新 cursor。任一步失败都恢复事务前状态。管理周期只能在 development set 上确定，test set 固定参数。

§5 Query-Time Access

查询开始时，Agent 获得用户问题、Recent Memory、Core Memory 和 compact structure map，而不是全部记忆正文。

方法或访问方式作用是否属于底层匹配
grep精确字符串或正则匹配；不建立额外索引是：Exact Lexical
bm25_search从文本构建稀疏索引，返回词法排序候选是：Sparse Lexical
embedding_search使用额外 Embedding 模型返回语义相似候选是：Dense Semantic
目录、文件、timeline、links、source resolution利用已有组织结构定位、展开和核验证据否：Structural Access

LLM 负责理解 query、生成或改写检索词、选择工具、判断候选相关性和停止检索，但不构成第四种底层检索方法。系统不规定固定的 BM25 → Embedding → LLM 流水线。

当前默认上限为 8 个 retrieval rounds、5 次工具调用和 10K memory-visible tokens。一个 retrieval round 表示一次 LLM 决策周期：模型可以结束回答，也可以提出一个或多个工具请求；工具返回后进入下一轮。因此，模型决策轮数与工具调用数是两个独立上限。单次 BM25 或 Embedding 最多返回 10 个候选。正式参数需要由 development-set budget sweep 确定。
