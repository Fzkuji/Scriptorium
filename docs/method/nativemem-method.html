Current Method Specification

Agent Memory Harness: File-Native, Source-Grounded Multi-View Memory

Agent Memory Harness 将 Source、Topic、Timeline、Recent、Core 和索引关系组织为一个文件式记忆状态。Topic 是可编辑的主要语义状态；Timeline、Recent 与索引由 Runtime 从 Topic 确定性生成。LLM 负责语义选择和组织，Runtime 负责身份、校验、同步与事务。

updated 2026-08-03 · current implementation and online contract

§1 Method Overview

CONTRIBUTION 01

File-native memory substrate

权威记忆保存在可读、可版本化的文本文件中。Source 只追加，Topic 可编辑，Core 独立维护；BM25 与 Embedding 只建立可重建的辅助索引，不保存唯一事实。

CONTRIBUTION 02

Source-grounded multi-view memory

系统在完整 Source Memory 之上维护 Topic、Timeline、Recent、Core 和跨视图索引。不同视图承担不同访问需求，同时通过稳定 memory ID 与 source references 保持一致。

方法按记忆生命周期组织：原始交互先进入 Source；Writer 从新增 Source 构建或更新 Topic；Runtime 由 Topic 生成 Timeline、Recent 和索引；Core 由 LLM 单独维护；查询 Agent 再按问题选择文件访问、grep、BM25 或 Embedding。下文分别说明状态结构、构建、管理和查询。

2.1 Source Memory

Source 保存完整消息和外部文档定位信息，是 Topic 事实的证据边界。对话来源使用 provider 提供的稳定 thread_id 与 message_id。如果输入数据只有顺序型 benchmark label，例如 LoCoMo 的 D1:14，Adapter 会在写入前将其确定性转换为 locomo/thread_*/msg_*；顺序 label 只用于 benchmark 输入和评测映射，不写入 NativeMem 的持久记忆。文件来源使用路径及页码、章节或行号。当前 Markdown link 的显示文字保留完整稳定 Source ID。Source 只追加，不因 Topic 修改、纠错或视图重建而覆盖。

2.2 Topic Memory and Memory Unit

Topic 是由 LLM 组织的 Markdown 语义状态。一个 memory unit 对应一个语义完整、可独立引用和更新的段落，而不是一句话或一个最小事实。相关的多项事实可以整合为连续正文，并分别保留来源注释；整个段落只在末尾保存一个 Obsidian-compatible block ID。

2.3 Derived Views

派生视图不接受 LLM 直接写入，也不保存 Topic 之外的唯一事实。每次 Topic 事务成功前，Runtime 全量扫描当前 memory blocks，并按下表生成或刷新对应状态。

派生状态输入确定性生成规则边界情况
Timeline每个 block 的 evidence footnotes每个具有 YYYY、YYYY-MM 或 YYYY-MM-DD 的 footnote 都按原始精度生成一个条目；条目使用该 footnote 前的事实片段，并链接到 Topic block 与对应 Source年份、月份和日期分别写入年度、月度和日级路径；undated 不生成文件或条目
Recent当前 blocks + Runtime 创建顺序以稳定 memory_id 的首次创建顺序排序，保留末尾 50 条改写、移动和换标题不改变顺序；新 ID 追加；删除或合并移除被删除 ID
Relations正文中的 #^memory_id links生成 outbound 与 backlinks，并按目标 ID 重写文件移动后的相对路径目标 ID 不存在时拒绝整个事务
Structure mapTopic 路径与 Markdown headings查询前按需生成紧凑目录，不保存语义副本不包含 Source 正文和 Runtime 私有状态
BM25 index当前条件可见的 Topic blocks 与 Source turns按文件 hash 解析文本；同一冻结 memory 与可见视图复用一份索引消融条件不可检索被隐藏的视图；不改变权威 Markdown
Embedding index与 BM25 相同的可见文本单元文档向量只编码一次，并在同一冻结 memory 的并发问题之间复用需要额外 encoder，但不要求向量数据库

Timeline 的日期不会由正文、文件修改时间、Git commit 时间或 session 结束时间推断。Topic evidence footnote 可以保存 YYYY、YYYY-MM、YYYY-MM-DD 或 undated。Writer 根据 Source observation date 解析明确的相对表达：“昨天”可解析为完整日期，“上个月”可解析到月份，“去年”可解析到年份。解析后的值只写入 footnote 的 Time 字段；YYYY、YYYY-MM 和 YYYY-MM-DD 都按原始精度进入 Timeline，不补造缺失的月份或日期；undated 只用于无法确定任何年份的事实，并且不进入 Timeline。同一事实在不同时间分别获得证据时，正文后连续放置多个 footnote，每个 footnote 只记录一个语义时间值。

2.4 Core Memory

Core 保存每次交互都需要提供的稳定信息，例如长期任务约束和持续偏好。它不是 Topic 的派生副本，也不进入 Recent FIFO。LLM 负责决定 Core 的保留、改写和删除；Runtime 执行 2K-token 上限并将其与 Topic 变更放在同一事务中。Core 可以使用与 Topic 相同的临时 block/evidence ID 和 bare Source handle；Runtime 将它们规范化为稳定 ID 与 Markdown Source links，并拒绝未定义、未使用或无法定位到 Source 的 Core footnote。Core 也可以通过 #^block-id 链接 Topic，而不复制 Topic 正文。

事实追踪方向始终回到 Source。Topic 和 Core 是需要保存的语义状态；Timeline、Recent、Relations、structure map、BM25 与 Embedding 索引均可重建。.nativemem/runtime.json 保存 session cursor、管理触发状态和完整创建顺序，它是运行状态，不是提供给模型的记忆正文。

§3 Memory Construction

构建只处理 session cursor 之后的新增 Source。Writer 使用普通文件命令直接编辑 staged Topic Markdown；它不提交事件 JSON，也不分别调用 Timeline、Recent 或 Relations 工具。一次写入事务如下。

3.1 Writer Capacity Calibration

不同模型即使声明相同的上下文窗口，也可能在多 session 记忆写入中表现出不同的来源覆盖率、格式稳定性和工具调用完成率。因此，Agent Memory Harness 在正式构建前对每个 model + Writer protocol 组合执行一次轻量校准。该过程测量当前 Writer 系统提示、批量写入提示、Claude Agent SDK 和工具契约共同作用下的有效输入容量，不把模型声明的最大上下文长度直接作为写入批量。

步骤处理判定
Fixed workload构造两组与 benchmark 无关、规模相同的合成事实 workload；每组包含固定的 20 个 session所有候选容量处理完全相同的全部消息和 source references
Capacity sweep按 2K / 4K / 8K / 10K / 12K / 14K / 16K 等候选容量，将 Writer system prompt、批量写入提示和消息一起计数容量只改变完成整份 workload 所需的批次数，不改变总任务
Message-boundary packing按原顺序贪心加入完整 message；下一条 message 导致超限时，将其整体放入下一批不截断 message 正文；session 可以跨批次；单条完整 message 超限时明确失败
Writer execution每个候选容量分别运行两组 probe，统计整份 workload 的 API 调用、输入/输出 token、耗时、成本、写入 blocks 和格式错误最终状态须覆盖全部预期事实和 source references；tool error 与 round limit 作为独立诊断项
Budget selection只比较两组 probe 内容均完整的档位以平均总成本最低者作为推荐预算，成本相同时比较平均总耗时；最大已测试通过档位另行记录
Build integration构建入口读取 calibration.json，校验 model、Writer protocol hash 和 tokenizer identity，再按推荐 token 上限分批只在原 session 的最后一条 message 完成后执行该 session 的验证与管理计数

校准产物保存 provider、model、Writer protocol hash、tokenizer、固定 workload hash、候选容量、批次数、调用次数、输入/输出 token、耗时、成本、事实与来源覆盖率、completion rate、推荐预算 safe_input_tokens 以及最大已测试通过档位。BuildConfig.calibration_path 指向该文件；未提供时保留显式 session_batch 作为可复现实验的固定回退。校准只决定 Writer 的增量输入预算，不改变 Source、Topic、Timeline、Recent、Core 或 Relations，也不构成新的检索方法。

此前 PackyAPI DeepSeek V4 Flash 的 16K 结果由旧的直接 API tool loop 产生，只保留为历史结果。迁移到 Claude Agent SDK 后，Writer protocol hash 已改变，旧校准产物会被拒绝；正式 benchmark 前必须按新协议重新校准，不能继续把 16K 作为当前推荐预算。

3.2 Agent Context and Tool Output

Writer 获得本批原始消息和当前 workspace structure。staged workspace 中的 Source 与派生视图可以读取，但只有 Topic 与 Core 可以修改；派生视图仍由 Runtime 在 Topic 修改通过校验后生成。

Writer prompt 只给出一条非强制建议：“建议先根据文件结构定位可能相关的文件，再查看其章节结构并读取必要内容；具体检索与编辑方式由模型决定。”系统不规定命令名、固定步骤或工具顺序。

Writer、Manager、verification 和查询都通过 Claude Agent SDK 执行。框架负责工具调用解析、provider 重试、工具错误返回和上下文管理；Harness 不再维护独立的 OpenAI chat-completions 循环、DSML 解析、工具输出缓存、固定工具调用次数或“无新增证据”停止逻辑。BM25 与 Embedding 仍使用 top_k，read_memory_file 仍支持 1-based offset / limit 行窗口。

每条 trajectory 使用临时 Claude 配置目录、bare 模式、禁用 session persistence，并只加载本次传入的 MCP 工具。它不读取用户的 ~/.claude 设置、插件或订阅登录态。endpoint、API key、model、轮次与成本上限均由入口参数传入；适配器只为子进程设置 Claude Code 所需配置，不修改父进程环境。

§4 Memory Management

管理以 Topic 修改为中心。LLM 对完整 Markdown 负责，包括正文边界、已有 ID 的保留、来源脚注和关系链接；Runtime 不重新判断段落语义，只执行可确定的规范化、校验、派生与事务操作。

4.1 Direct Topic Editing Contract

LLM 通过共享 shell 直接修改 Topic 文件，不调用逐字段 add、update、split 或 merge 工具。所有操作遵守同一文件契约：

语义操作LLM 必须写入的结果Runtime 自动处理
新增完整段落、新 evidence footnotes、一个 ^new-block-label分配稳定 ID、解析 Source、追加 Recent 顺序
补充或改写直接修改原段落；保留原 block ID；保留仍有效的 footnotes，并为新增事实补充证据刷新 Timeline、Recent 内容和关系
拆分一个结果段落保留原 ID；其余段落各用不同的新临时 ID；footnotes 跟随其支持的事实为新增段落分配 ID，保留原段落创建顺序
合并保留一个原 ID；合入仍有效正文和 footnotes；同一事务删除或改写指向被移除 ID 的 links移除被合并 ID 的派生记录；检测 dangling links
移动或重命名移动文件、heading 或完整段落；block ID 不变按目标 ID 改写跨文件相对路径，并刷新所有视图
纠错删除删除 Topic 段落及其 footnote 定义，并同时处理所有入链Source 不删除；Timeline、Recent 和 Relations 移除对应项

每个 Topic 非标题正文段落都必须以一个合法 block ID 结束，并至少包含一个已定义的 evidence footnote。已有段落保留原 block ID；新段落必须使用 ^new-block-<label>，Runtime 再生成 8 位十六进制稳定 ID，不能由模型自行拼接稳定 ID。若候选 ID 已存在且对应不同记忆，Runtime 会使用递增计数器重新计算，直到获得当前 memory tree 内唯一的 ID。evidence ID 允许连字符和下划线。Runtime 将正文 marker 统一为 正文[^evidence-id] ^block-id：evidence citation 前不留空格，block ID 前只留一个空格。重复 ID、未定义或未使用的 footnote、无效 Source、Topic 间链接缺少 #^block-id、关系目标不存在、直接修改 Source 或派生视图，都会使事务失败。Runtime 丢弃 staged 修改并保持安装状态不变；错误返回给 Agent 后由其修正文件。

旧版 save_memory(events[]) 和 Reconciler 代码仅用于读取或迁移旧格式，不暴露给当前 Writer、局部 Manager、全局 Manager 和 repair Agent；当前主流程只使用上述 Markdown 契约。

4.3 Fact Evolution, Ordering, and Transactions

现实状态变化与事实纠错分开处理。状态变化应保留旧状态及其日期，再写入具有新 evidence 的状态；事实纠错可以删除或替换错误的 Topic 内容，但不会删除 Source。若改写删除了某项事实，其 evidence citation 和定义也必须在同一文件修改中删除；保留的事实必须继续有来源。

顺序定义
Source保持原始消息数组、JSONL 或时间戳顺序，不受 Topic 编辑影响
Topic按引用在 Markdown 中的出现顺序，由 LLM 决定
Timeline按 evidence 日期分文件；同一天内按主要 Source handle，再按 memory_id 确定性排序
Recent按首次创建顺序维护；普通改写和移动不改变顺序，新 ID 追加到尾部

一次管理事务依次执行：暂存 Topic/Core 修改、物化临时 ID、解析全部 blocks、规范化 Source 和关系链接、校验 ID/source/link 完整性、重建 Timeline/Recent/Relations、原子安装、创建 Git commit、最后更新 cursor。任一步失败都不推进 cursor，并恢复事务前的已安装状态。管理周期只能在 development set 上确定，test set 固定参数。

§5 Query-Time Access

查询开始时，Agent 获得用户问题、Recent Memory、Core Memory 和 compact structure map，而不是全部记忆正文。

方法或访问方式作用是否属于底层匹配
grep精确字符串或正则匹配；不建立额外索引是：Exact Lexical
bm25_search从文本构建稀疏索引，返回词法排序候选是：Sparse Lexical
embedding_search使用额外 Embedding 模型返回语义相似候选是：Dense Semantic
目录、文件、timeline、links、Source 文件利用已有组织结构定位、展开和核验证据否：Structural Access

LLM 负责理解 query、生成或改写检索词、选择工具、判断候选相关性和停止检索，但不构成第四种底层检索方法。系统不规定固定的 BM25 → Embedding → LLM 流水线。

Source Memory 是普通、可检索的 Markdown 文件。目录浏览、文件读取、grep、BM25 和 Embedding 始终可以直接访问 Source，不要求 Agent 先从 Topic 获得 source ID，也不使用单独的 resolve_sources 工具。函数参数 retrieval.QueryConfig(verify_sources=True|False) 只控制 prompt 是否要求查询 Agent 在回答前核验相关 Source；设为 False 时核验变为可选，不改变 Source 可见性或工具集合。每题 termination trace 保存实际参数值。运行配置由入口显式构造并作为函数参数传递，不从父进程环境读取。

当问题明确给出日历时间范围，或者 Agent 已经从证据中解析出日历范围时，Agent 可以在同一次 bm25_search 或 embedding_search 调用中附加可选的 date_from 和 date_to。两个参数均接受 YYYY、YYYY-MM 或 YYYY-MM-DD，不需要额外的时间抽取模型调用。没有明确时间约束时省略参数；“搬到上海之前”一类尚未确定锚点日期的表达不能直接用于硬过滤。

输入或状态LLM 操作Runtime 操作
无明确日历时间只提交 query，不传时间参数不改变 BM25 或 Embedding 的候选集合
明确年份、月份或日期在现有工具调用中填写可选 date_from / date_to校验日历值，并按输入精度展开为内部半开区间
只有起点或终点只填写已确定的一侧形成开放时间区间；两个边界逆序时拒绝调用
Topic 段落包含多个 evidence 时间无额外处理按 evidence 支持的事实片段建立候选；任一 evidence 区间重叠即可保留
只有 undated evidence无额外处理无时间过滤时保留，使用硬时间过滤时排除

Runtime 将 2022 展开为 [2022-01-01, 2023-01-01)，将 2022-07 展开为 [2022-07-01, 2022-08-01)，将 2022-07-20 展开为 [2022-07-20, 2022-07-21)。date_to 包含其指定精度的完整年份、月份或日期。候选过滤使用区间重叠，之后才执行 BM25 词法排序或 Embedding 相似度排序。同一段落分别具有 2019 年和 2023 年 evidence 时，这两个时间保持离散，不能合成为连续的 2019–2023 范围。

read_memory_file 是代码暴露给模型的受限文件读取工具：它校验相对路径，并只允许读取当前检索条件可见的文件。Native 条件同时提供只读 shell；不提供 shell 的检索消融条件依赖该工具。它支持可选的 1-based offset / limit；省略时读取全文，提供时只返回相应行窗口。Prompt 只建议先定位相关文件与章节，不规定命令或工具顺序。

Writer、verification、局部 Manager、全局 Manager 和查询统一由 Claude Agent SDK 管理，默认每条 trajectory 最多 20 个模型轮次，并可设置 max_budget_usd。Harness 不设置独立工具调用上限或 memory-visible-token 停止条件。实际轮次、工具调用数、可见 token、停止原因、耗时和框架报告成本保留为评测记录。
