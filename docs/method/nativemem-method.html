Current Method Specification

NativeMem: File-Native, Source-Grounded Multi-View Memory

NativeMem 使用普通文本文件保存外部长期记忆。LLM 负责记忆语义、具体组织位置和查询动作；Runtime 负责引用、日期、路径、链接、预算与文件级原子更新。Git commit 与 session cursor 的在线事务仍属于目标规范。

updated 2026-08-01 · V11 benchmark implementation + target online contract

§1 Method Overview and Contributions

CONTRIBUTION 01

File-native memory substrate

Source Memory 与派生记忆均保存在可读、可版本化的文本文件中；Source 只允许追加，派生记忆可以编辑和重组。grep 直接读取文件；BM25 与 Embedding 只建立可以从文本重建的辅助索引，不保存唯一事实。

CONTRIBUTION 02

Source-grounded multi-view memory

系统在完整 Source Memory 之上同时维护 Topic、Timeline、Markdown links/backlinks、Recent Memory 和 Core Memory，并使用共同的 source references 回到原始交互。

视图类型由系统定义。Agent 决定具体保存内容、topic path、文件、章节、链接和检索动作；Runtime 不替代语义决策，只执行可验证约束。

§2 Memory State

session t 的记忆状态定义为 M_t = (S_t, A_t, R_t, C_t)，其中 A_t = (T_t, D_t, G_t)。

状态文件表示职责
Source Memory Ssources/*.md追加保存完整原始交互；使用稳定 source IDs；不摘要、不覆盖
Topical View Ttopics/**/*.md按实体、项目或主题组织长期派生记忆
Temporal View Dtimeline/YYYY/MM/DD.md 或 timeline/undated.md按事件时间提供访问入口；无法确定日期时进入 undated
Hyperlink Relations G嵌入 Topic 与 Timeline 的 Markdown links；指向 Source 的单向 source referencesTopic 与 Timeline 之间显式维护 links/backlinks；Source 保持追加且不可修改，Source 侧反向关系由 Runtime 扫描 references 临时生成
Recent Memory Rrecent_events.jsonl保留最近写入的 50 条记录；超过容量时 FIFO 移除最早记录
Core Memory Ccore.md保存每次交互都需要提供的稳定信息；当前上限为 2K tokens
 
memory/
├── sources/
├── topics/
├── timeline/
├── recent_events.jsonl
└── core.md

G_t 没有独立目录。Topic 与 Timeline 文件物化双向 links；它们使用单向 source references 指向不可变的 Source 文件。Source 侧反向关系由 Runtime 扫描 references 临时生成，不回写 Source。BM25 与 Embedding 索引也不属于 M_t：它们是可删除、可重建的查询缓存；session cursor、scheduler 和 Git 运行状态位于 Runtime，而不写入记忆正文。

Runtime 在查询开始时从目录路径和 Markdown headings 临时生成 compact structure map。该 map 不持久化，文件变化后重新生成，并计入查询的 memory-visible-token budget。

2.1 Memory Unit and Fields

一个记忆单元表示一条可以独立追踪来源和时间的事实或事件，但它不要求在 Topic 文件中独占一行。Topic 是由 LLM 自由编辑的 Markdown；记忆单元通过正文后的 footnote ID 与来源定义保持身份。JSON 只用于首次写入和 Runtime 内部 reconciliation，不是权威存储格式。

字段产生者示例定义
memory_idRuntimemem_7f31c2记忆单元的稳定唯一标识，与来源 ID 分离；内容、日期或 Topic 位置更新时保持不变。
contentLLM 直接编辑用户于 2026 年 7 月搬到上海。footnote ID 之前对应的自然语言正文；可以位于连贯段落中，不要求列表式记录。
whenLLM / Reconciler 判断，Runtime 校验2026-07-20事实发生时间，而非写入时间；无法确定时进入 undated。
source_refsLLM / Reconciler 选择，Runtime 解析["src_17", "src_41"]一个或多个真实消息或文件来源。临时 handle 在提交前转换为稳定的 message ID、文件路径和定位信息。
topic_path由 LLM 编辑后的文件位置表示topics/personal/residence.md不重复写入记忆正文；Runtime 从实际 Markdown 路径读取。
heading由 LLM 编辑后的标题层级表示居住经历不重复写入记忆正文；Runtime 从 # 标题层级读取。

Source candidates

Runtime 为当前新增消息、已有引用以及 Agent 本轮实际读取过的文件建立候选来源表。对话来源保留原系统的 thread_id 与 message_id；文件来源保留路径以及页码、章节或行号。来源 handle 只在当前写入或 reconciliation 中使用。

{
  "src_17": {
    "type": "message",
    "thread_id": "thread_123",
    "message_id": "msg_a8f2"
  },
  "src_41": {
    "type": "file",
    "path": "documents/employment-contract.pdf",
    "title": "劳动合同",
    "page": 2
  }
}

title、文件路径和页码均由 Runtime 从文档元数据、正文标题、文件名及解析结果中获取，不由 LLM 编写。标题获取顺序为：文档元数据标题、正文标题、原始文件名。缺少标题时直接显示文件名，不根据内容生成新标题。

Initial write

首次从新 Source 构建记忆时，Writer 可以用一次结构化调用提交需要语义判断的内容：

{
  "content": "用户于 2026-07-20 搬到上海。",
  "when": "2026-07-20",
  "source_refs": ["src_17", "src_41"],
  "topic_path": "personal/residence.md",
  "heading": "居住经历"
}

Authoritative Markdown

Runtime 校验来源、生成 memory_id 并插入 footnote。之后 LLM 直接编辑这份 Markdown，不需要为普通更新调用 update_memory：

## 居住经历

用户于 2026 年 7 月搬到上海。[^mem_7f31c2]
同年 8 月搬到浦东，并开始在新公司工作。[^mem_21ab90][^mem_a8d910]

[^mem_7f31c2]: 2026-07-20 · Sources: [项目迁移讨论 · “我准备下个月搬到上海……”](../../sources/thread_123.md#msg_a8f2)
[^mem_21ab90]: 2026-08-03 · Sources: [居住地点更新 · “现在已经搬到浦东……”](../../sources/thread_456.md#msg_b31d)

一个段落被解析为交替出现的正文片段和引用组。每个引用组对应从段落开头或上一个引用组之后开始、到当前引用组之前结束的正文；连续的多个 ID 共同对应同一段正文。标题、代码块和 footnote 定义不参与正文解析。

Direct editing and automatic reconciliation

LLM 可以直接重命名标题、移动段落、调整顺序和改写正文。一次文件写操作结束后，Runtime 比较修改前后的 Topic：

修改处理方式
只改变标题、路径、顺序、空白或 Markdown 格式代码根据保留的 ID 直接同步，不调用 Reconciler
已有 ID 对应的正文发生变化自动调用 Reconciler，判断是同一事实改写还是新增事实
新增无 ID 正文、拆分、合并或旧 ID 消失自动调用 Reconciler，恢复新旧记忆对应关系
找不到有效来源的新事实拒绝提交并恢复修改前状态

Reconciler 只读取修改过的章节、受影响的旧记忆和有限候选来源，并在 Runtime 内部返回旧 ID 对应、新记忆正文、日期和 source handles。编辑 Agent 不生成这份 JSON，也不额外调用记忆更新工具。Runtime 校验正文必须存在、来源必须真实、旧 ID 不得隐式删除，然后分配新 ID 并重建派生视图。

Ordering and updates

顺序定义
Source保持原始消息数组、JSONL 或时间戳顺序，不受 Topic 编辑影响
Topic按引用在 Markdown 中的出现顺序，由 LLM 决定
Timeline按事件时间排序；同一时间按主要 Source 时间，再按 memory_id
Recent按首次创建顺序维护；普通改写和移动不改变顺序，新 ID 追加到尾部

现实状态后来变化时新增带时间记忆，不覆盖旧事件。普通文件改写不能隐式删除旧 ID；删除错误派生记忆必须使用显式纠错操作，且 Source 永不删除。所有校验和跨视图生成完成后才原子替换文件并创建 Git commit；失败时回滚整次修改。

实现边界：以上是目标规范。当前 V11 已有 staged Topic、跨视图同步、ID/Source 校验和失败恢复，但仍使用 HTML comment marker 与固定单行事件；自由 Markdown footnote 解析和自动 Reconciler 尚未实现。

§3 Topical View Structure

topics/ 是主要语义视图，采用“目录 → Topic 文件 → 章节 → 事件记录”。目录和文件名由 Agent 根据未来检索位置选择，不预设固定 taxonomy。

topics/
├── people/
│   └── Caroline.md
├── projects/
│   └── native-memory.md
└── themes/
    └── lgbtq-support.md
# Caroline

## Education and Career

Caroline plans to pursue counseling or mental health work. She later began preparing applications for relevant programs.[^mem_a4c921][^mem_3c7120]

[^mem_a4c921]: 2023-05-08 · Sources: [Career planning · “I plan to pursue counseling…”](../../sources/thread_caroline.md#msg_31)
[^mem_3c7120]: 2023-06-02 · Sources: [Application planning · “I started preparing…”](../../sources/thread_caroline.md#msg_52)

目标规范是一份文件只使用一个一级标题，二级或三级标题表示不同方面。正文可以保持连贯，事实或事件通过稳定 footnote ID 连接一个或多个 source references。跨 Topic 关系通过共同 ID 与可重建索引解析；同一事件不应在多个 Topic 文件中保存彼此独立的完整副本。

当前 V11 已支持目录、文件、章节和事件链接，但仍可能产生一个文件多个一级标题或跨 Topic 重复记录。正式实现需要将上述目标规范加入 Runtime 校验。

§4 Memory Construction

新交互首先追加到 Source Memory。Writer 读取新增交互、当前 Topic inventory 和必要局部上下文，提出待写入内容、topic path、章节、事件日期、links 与 Core 更新。Runtime 再执行以下确定性操作：

  • 校验 source references、路径和日期；
  • 物化 Topical 与 Temporal View，维护两个派生视图之间的 links/backlinks，并添加指向不可变 Source 的单向 references；
  • 更新 Recent Memory 的 50 条 FIFO 窗口和 Core token 上限；
  • 检查跨视图 event IDs 与 source coverage；
  • 原子替换受影响文件，失败时恢复修改前状态。

首次写入完成后，Writer 与 Manager 可以直接编辑 Topic Markdown。只改变组织位置的修改由 Runtime 确定性同步；事实正文发生变化时，Runtime 自动执行局部 reconciliation，再统一提交 Topic、Timeline、Recent 与索引。该过程不要求编辑 Agent 使用逐字段更新接口。

事实变化采用完整时间记录。旧事件和新事件均保留各自的时间与 source references；查询时由 Agent 根据问题时间范围和事件顺序判断，不通过覆盖旧 item 维护单一 current state。

§5 Three-Level Memory Management

三级管理表示三种触发时机和作用域，不是三种存储层级。下表中的在线触发属于目标 Runtime 规范；当前 V11 benchmark 使用对应的静态映射。

管理过程目标在线触发V11 benchmark 映射作用域
Incremental Writing未处理内容达到 token/context 阈值，或 session 一小时没有新消息逐个读取预先给定的静态 session只处理 cursor 后的新增交互及直接相关 Topic
Periodic Local Reorganization按写入批次或新增 token 阈值每累计固定数量 session 调用局部 Manager只整理本周期发生新增写入的 Topic
Daily Global Management每天最多一次，且上次管理后存在新的写入 commit全部输入结束且存在新增记忆时调用一次全局 Manager跨 Topic 调整目录、文件、章节与链接；没有新增记忆时跳过

局部整理周期只能在 development set 上确定。test set 使用固定参数，不能根据测试问题的检索结果反复修改记忆结构。

§6 Query-Time Access

查询开始时，Agent 获得用户问题、Recent Memory、Core Memory 和 compact structure map，而不是全部记忆正文。

方法或访问方式作用是否属于底层匹配
grep精确字符串或正则匹配；不建立额外索引是：Exact Lexical
bm25_search从文本构建稀疏索引，返回词法排序候选是：Sparse Lexical
embedding_search使用额外 Embedding 模型返回语义相似候选是：Dense Semantic
目录、文件、timeline、links、source resolution利用已有组织结构定位、展开和核验证据否：Structural Access

LLM 负责理解 query、生成或改写检索词、选择工具、判断候选相关性和停止检索，但不构成第四种底层检索方法。系统不规定固定的 BM25 → Embedding → LLM 流水线。

当前默认上限为 8 个 retrieval rounds、5 次工具调用和 10K memory-visible tokens。一个 retrieval round 表示一次 LLM 决策周期：模型可以结束回答，也可以提出一个或多个工具请求；工具返回后进入下一轮。因此，模型决策轮数与工具调用数是两个独立上限。单次 BM25 或 Embedding 最多返回 10 个候选。正式参数需要由 development-set budget sweep 确定。

§7 Implementation and Evidence Boundary

状态内容
V11 benchmark 已实现不可变 Source、Topic、Timeline、派生视图间 links/backlinks、单向 source references、静态 session Writer、固定周期局部 Manager、结束时全局 Manager、Recent 50、Core 2K、文件级原子恢复、BM25、Embedding 与检索预算
在线 Runtime 尚未实现Git commit + session cursor 事务、按 token 增量触发、一小时空闲触发和按自然日运行的 scheduler
仍需实验确认Recent、Core、周期整理、BM25、Embedding 和 Agent-controlled retrieval 的独立贡献与成本；Topic 规范化对重复和检索效率的影响

已有 LoCoMo 与 LongMemEval 结果只能归属于产生这些结果的既有版本。新增组件必须在相同 memory、answerer、judge 和预算下分别消融，不能由旧结果直接推导效果。
