# v10 — 固定最终结构，显式化建库策略

> 2026-07-16。实现：`src/v10_memory.py` 与
> `src/adapters/run_nativemem.py`。v10 不修改 LoCoMo 评分器。

## 10.1 版本定位

v10 以现有对照中质量最稳定的 `v8.8+calendar` 为默认设计，不采用
v9 的整 session 两级转写。现有证据是：固定 6-turn 切块的对照均值为
92.4，整 session 的 v9 为 89.6；七组匹配比较中，v8.8 没有低于 v9。

v10 的默认执行路径保留 v8.8 的 writer prompt、覆盖检查、日历信息、
双视图存储、`dia_id` 原文索引、整理逻辑和单模型检索答题。它只把三个
原来分散在代码和环境变量中的建库决策集中成独立配置。

## 10.2 默认设计

一次建库按以下顺序执行：

1. 每 6 个 dialogue turn 组成一个写入片段。
2. writer 读取当前片段、当前话题目录、同一 session 最近 20 条已提炼
   事件摘要和代码生成的日历信息。
3. writer 输出原子事件；代码校验 `refs`，转换为真实 `dia_id`，写入
   `topics/` 与 `timeline/`。
4. 每个 session 结束后，对本 session 涉及的话题执行 1 次去重、话题
   收敛和分节整理。
5. 所有 session 结束后，对全部话题执行 1 次最终整理。
6. 检索与答题继续使用 v8.8 的双视图和单模型路径。

前序上下文只在同一 session 内保留，切换 session 后清空。默认携带的是
已提炼事件，不是全部原始对话，因此上下文长度有固定上限。

## 10.3 三组建库参数

| 决策 | 环境变量 | 默认值 | 含义 |
|---|---|---:|---|
| 写入频率 | `NATIVEMEM_V10_WRITE_TURNS` | `6` | 每次 writer 处理多少个 turn；`session` 表示整段 session |
| 前序信息形式 | `NATIVEMEM_V10_CONTEXT_MODE` | `events` | `events/raw/summary/none` |
| 前序信息数量 | `NATIVEMEM_V10_CONTEXT_ITEMS` | `20` | `events` 模式为事件数，`raw` 模式为 turn 数 |
| 摘要上限 | `NATIVEMEM_V10_SUMMARY_MAX_WORDS` | `180` | 仅 `summary` 模式使用 |
| session 整理间隔 | `NATIVEMEM_V10_TIDY_EVERY_SESSIONS` | `1` | 每多少个 session 整理一次；`0` 表示关闭 |
| session 整理次数 | `NATIVEMEM_V10_SESSION_TIDY_PASSES` | `1` | 每个整理边界重复多少次 |
| 最终整理次数 | `NATIVEMEM_V10_FINAL_TIDY_PASSES` | `1` | 全部 session 后重复多少次 |

四种前序信息模式的语义：

- `events`：携带最近若干条已提炼事件。默认值与 v8.8 完全一致。
- `raw`：携带最近若干个原始 turn，只用于指代和话题延续，不再次提取旧事实。
- `summary`：携带一个滚动摘要。摘要与事件在同一次 writer 返回中更新，
  不增加独立的摘要请求。
- `none`：writer 只看当前片段和话题目录。

这些非默认模式是成本消融项，目前没有新的 LoCoMo 全量结果，不能把它们
记为最终性能配置。

这里的“整理 1 次”指一次整理流程，不等于一次 LLM 请求。默认分节配置下，
一个达到整理阈值的话题可能分别触发同义行合并和分节两个请求；没有达到阈值
的话题不会触发这两个请求。因此实际整理成本还取决于本次涉及的话题数和每个
文件新增的未整理行数。

## 10.4 运行方式

```bash
export NATIVEMEM_PROMPT=v10
export NATIVEMEM_V8_SINGLE=1
python3 src/adapters/run_nativemem.py \
  --sample 0 \
  --output results/nativemem-v10-s0/questions.json
```

只研究建库而不执行检索答题时使用 `--build-only`。该模式只输出
`_build_stats`，生成的 memory 目录可以在后续固定 retriever/answerer 的
运行中通过 `--memory-dir` 复用。v10 复用时还必须传入原始
`--source-build-record`；程序会核对 sample、memory 路径、writer 模型和配置，
不允许把当前 retriever 模型误记成原 writer 模型。

输出的 `_build_stats` 会保存 `method=NativeMem-v10` 和完整
`v10_config`，并在 `build_phase_usage` 中分别记录提取、补抽与整理调用，
同时保存 `max_sessions`，避免 smoke test 使用全量问题作为覆盖率分母；这些字段
用于避免后续只保留总成本而无法解释成本来源。

正式实验还必须设置 `NATIVEMEM_FAIL_FAST=1` 和
`NATIVEMEM_OPENAI_MAX_RETRIES=0`。前者使任何 API 错误立即终止，后者避免
OpenAI SDK 重试与 writer 业务重试叠加。缺少这两个设置时，历史兼容路径可能在
请求全部失败后返回空事件，不能用于实验。

LoCoMo 评分仍只允许使用仓库固定的 `scripts/eval_full.py`；v10 没有新增、
复制或修改评分脚本。

## 10.5 当前证据边界

v10 默认配置继承的是已比较过的 `v8.8+calendar` 设计，因此可以把该设计
作为 v10 的选定默认值。v10 代码本身目前只有实现与回归测试，尚未产生独立
的全量 benchmark 分数。后续只有改变三个策略参数时，才需要重新建库；对已
生成答案的统一评分不属于 v10 建库设计的一部分。
